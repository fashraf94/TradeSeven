## 0a. What the pilot is

One archetype (Trend Follower), one game (BaggerBomb), one journey a player completes end to end: an idea goes in → the agent researches it honestly → they discuss it → it becomes a saved, versioned hypothesis with a time-frame → it is frozen into a battle at deploy → every decision about it is recorded with what the agent actually saw → the Film Room replays believed / called / done. The agent's learning stays frozen for the pilot's comparisons, and live activation is gated per mode. Success is journey integrity — never P&L (Charter; audit §10). Formally: the minimum-change connection of components the audit classified reuse/extend, closing G06 under R6/R7, qualified in an isolated advisory stage before any authority. Acceptance is the audit's cases A–I.

## 2. The Hypothesis contract

**2.1 Content — immutable, new build (F04).** At HEAD, edit rejection applies to `committed` status only, uncommit re-opens in-place editing, and equip identity is `watchlistId` alone — so versioning is new construction. P1 builds hypothesis **content versions** as server-only-written records in a `hypothesisVersions` subcollection on the saved list. Content fields — `statement`, `horizonEnum` + `source`, `activation[]`/`invalidation[]` conditions (each `{symbol, side, level, basis}`), `evidenceRefs[]`, `publishedAt?` (provenance-or-unknown, distinct from `referencedDate`/`createdAt`), origin discriminant — are **write-once**, hashed into the version's own `contentHash`. Server-owned version allocation runs in a transaction with an expected-version concurrency check; creation takes a caller-supplied `opId` so retries never mint duplicates. **Version-aware equip identity:** equip compares `{watchlistId, hypothesisVersion}`; re-equipping a newer version is a real change, never an idempotent no-op.

**2.2 Lifecycle — a separately governed envelope (V11-04).** Lifecycle lives beside the content in the same record family but under its own rules: the mutable fields are exactly `status`, `firstDeployedAt` (stamped once, transactionally, at the version's first deploy and never rewritten), `stateChangedAt`, `stateSource`, `stateReason`, and `successorVersion?` (set when a future version supersedes it). None of these enters `contentHash`, config identity, or the battle's frozen content. The state machine: `draft → researched → ready | waiting_for_evidence → activated → invalidated | review_due | retired`, plus the pre-deploy terminals `rejected` and `cancelled`, each carrying a typed reason (V12-05). The watchlist's own draft/committed status is not repurposed as this lifecycle. Uncommit/delete/recommit: a version ever equipped or committed keeps immutable content forever; edits are rejected with a save-as-future-version offer; parent-list deletion soft-deletes and never destroys versions referenced by battles. `review_due` never grants exit authority and never deletes anything (R6).

**2.3 One writable truth.** The legacy PATCH surface continues to ignore hypothesis fields; hypothesis content changes flow only through version creation. Precedence declared: `hypothesis.statement` is the truth for pilot consumers; the legacy `thesis` string — which remains writable on a draft today — is preserved for legacy consumers and is not a second writable copy of the hypothesis; P1 documents which consumers read which, and no consumer reads both.

**2.4 Hash and snapshot discipline (F07, resolved design retained).** The input projection of `equippedConfigHash` is pinned exactly as it is today. The full hypothesis content rides the battle context as a new **sibling** field, `equippedHypothesis` (content fields + `hypothesisVersion` + `contentHash`), never inside the hashed `equippedWatchlist` object — so existing hash semantics, Backing's stake-vs-settlement comparison, and all historical values are untouched. The existing snapshot keeps tickers as strings, byte-for-byte. Lifecycle fields never enter any identity. No historical manifest, stake, or vintage is ever recomputed. Any future hash widening is its own versioned change coordinated with the Backing owner — not this spec.

**2.5 Horizon, conditions, and the transition table (F08, V11-04).** The parse's horizon **enum is carried exactly** (`intraday | swing | positional | longterm | unspecified`) as `{horizonEnum, source}`; manual/screener origins without a session carry `unspecified` unless the player sets one. The enum→window translation table is authored in the R5 companion (R6's method, wall-clock market time, never check counts) and is the only place windows are defined; the call-record contract's own phrase table (`next_check`/`this_session`/`this_battle`/`explicit`) is a distinct input domain for short-lived declarations — two tables, two record kinds, both citing R6, never merged. Intraday-origin ideas keep their stated enum, translate to the mode's shortest daily-basis window, and never license intraday evidence. The review clock for a version anchors at its `firstDeployedAt`; undeployed versions have no clock; `unspecified` runs no clock and reaches `review_due` only at battle end.

Transitions (actor · precondition · reason) — the complete table (V12-05):

| From → To | Actor | Precondition | Reason |
|---|---|---|---|
| draft → researched | the research-completion writer (P2's host record close) | a `researchWork` record completed for this version's content | `research_complete` |
| researched → ready | player action (P1) | player confirms the hypothesis | `player_ready` |
| researched → waiting_for_evidence | player action or dialogue outcome (P1) | the missing evidence is named on the record | `awaiting_evidence` |
| waiting_for_evidence → ready | player action (P1) | player confirms after the named evidence arrives | `evidence_supplied` |
| draft \| researched \| waiting_for_evidence → rejected (terminal) | player action | explicit reject | typed player reason |
| any pre-deploy → cancelled (terminal) | player action | explicit cancel | typed player reason |
| ready → activated | deploy transaction (P1) | version equipped at battle creation; stamps `firstDeployedAt` once | `deployed` |
| activated → review_due | evaluation encounter, or close-of-day sweep (deferred-beat dependency) as backstop | horizon window elapsed per the companion table | `horizon_elapsed` |
| activated (`unspecified` horizon) → review_due | battle completion's transaction (the existing completeBattle host) | the battle ended | `battle_ended` |
| activated → invalidated | evaluation encounter | a typed invalidation condition met, or cited evidence withdrawn | typed condition/withdrawal reason |
| any non-terminal → retired (terminal) | player action | explicit retire | `player_retired` |
| review_due → (state kept, `successorVersion` set) | player reaffirmation | **reaffirmation creates a new future content version** (identical content permitted); the new version's clock starts at *its* first deploy; the due version's clock is never reset | `superseded` |

**Judged once (parity with the contract's H2):** every transition is a committed transaction whose fresh read must find the version in the prior state; an unconfirmed write may commit late, and a later transaction acts only if its own fresh read still finds the prior state — so a horizon boundary is judged exactly once, never twice and never by a stale read. **Deploy admission (V12-05):** `ready` deploys and stamps `firstDeployedAt` once; re-deploying an **already-activated, still-current** version is admission-idempotent — no restamp, state unchanged; a **`review_due`** version may be viewed and acknowledged and continues within its current battle, but a **new deploy requires the future `ready` version created by reaffirmation** — acknowledgment alone never re-admits a due version and never resets any clock. (This supersedes V1.2's looser re-equip-with-acknowledgment rule; R6 is honored — review ritual, no forced action, and reaffirmation is one action producing the redeployable version.) Legacy string condition arrays remain descriptive and unmonitored, preserved as-is.

**2.6 The shared ref union — content predicate (F06, V11-06; joint amendment with the call-record contract).** `hypothesisRef` is a three-way union chosen from the **frozen battle context's content, never the calendar**: **versioned** `{watchlistId, hypothesisVersion}` when the frozen context contains a validated version; **legacy** `{watchlistId, equippedConfigHash}` whenever the frozen context carries equipped provenance *without* a version — both branches omit `battleId` inside battle-scoped records (calls, capture, receipts all are), and a ref traveling in any record that is not battle-scoped carries `battleId` beside it — whatever the battle's creation date, since unversioned committed lists remain equip-eligible after P1 on paths the pilot doesn't activate; and **null** in exactly two typed situations, distinguished by `origin`, never by the null alone. **The complete rule (V13-01), identical in the call-record contract:** `origin ∈ {equipped, agent_initiative, provenance_unresolved}` — `equipped` carries a validated versioned or legacy ref; `agent_initiative` carries `hypothesisRef: null` because no equipped hypothesis origin exists; `provenance_unresolved` carries `hypothesisRef: null` plus a `provenanceReason` because frozen provenance exists but is unusable (a present-but-unusable snapshot; per H1 an absent or null frozen watchlist is `agent_initiative` regardless of config hash, since the hash is computed over the whole manifest and always exists — it proves nothing about provenance) — visible and conservative, never read as initiative. Readers never infer origin from a null ref alone; the origin discriminator is part of the shared validation and reader contract, including the Film Room projection. A missing version by itself still selects the legacy branch whenever valid legacy provenance exists; no reader resolves the current saved list as historical meaning; malformed *new pilot* records are rejected without breaking accepted legacy records. Only new legacy *emission* retires where the input is versioned; legacy readers are permanent. No migration or retroactive versioning.

**2.7 Privacy projection.** Non-owner and completed-battle projections must not expose the hypothesis statement or source refs through the shared battle shape: P1 preserves the current active-battle exclusion and adds an explicit rule for `equippedHypothesis` on completed-battle views — owner sees full, others none in v1. A P1 acceptance item.

**2.8 Origins and parse binding.** Origin variants are typed, never faked: SignalDrop; theme (synthetic dropId, `source: theme`, discriminant carried through save — no fabricated SignalDrop join); screener (`sourceScreenSpec`); manual. A discriminated union, one reader. **Parse binding (restated in full per V11-08):** the dialogue loads the server-stored parse by dropId as authoritative rather than trusting a client envelope that merely matches the contentHash; text entry preserves an entered source URL as attribution without changing what is parsed. This is a behavior change to existing dialogue output and ships as its own founder-approved flip inside P1 — never smuggled as metadata.

## 3. Research work package (F10, V11-05)

Each origin names its **host**: SignalDrop and theme → the dialogue session; screener → the screener chat session (`researchSessions`, whose persisted message budget is the budget currency); manual → a standalone `researchWork` record with no session host. Every record mints a stable `researchWorkId` at creation — the identity §8 points at.

**Counting (corrected algebra).** Stage counts are **cumulative** — each symbol counted once *per stage* it reached within the declared research run: `universeSize` (the screener's own input population, unchanged in meaning), `matchedPreLimit` (the screener's matchCount, unchanged), `returned/shortlisted`, `selectedForInvestigation`, `investigationsCompleted`, `eligible`. A symbol that ends eligible therefore also counts in every stage it passed — the funnel is the evidence. Only **terminal outcomes** are disjoint within the declared cohort: `eligible | rejected(reason) | dataMissing | cancelled/failed(terminalReason)`. The cohort is the union of screener-returned symbols and user additions; out-of-universe user additions join the cohort flagged `offUniverse` without redefining `universeSize`. Repeated attempts live in telemetry, not counts.

**Budget and telemetry.** `budget = {allotted, used}` in the persisted-message currency, named as such. Per-stage telemetry: attempts and completions, tokens when the provider supplies them else `unknown` (never fabricated), elapsed time, cancellations and failures (which spend attempts without burning message budget — recorded, not free), terminal reason. Per-stage deadlines and retries preserved, not unified. Zero qualifying opportunities remains a valid, honest completion.

## 4. Opportunity and origin accounting (G05)

## 6. Brain output — intent is not execution (F09, V11-07)

Protective actions keep R3's outcome vocabulary untouched. **Canonical wire enum:** `fired_replaced | fired_slot_empty | mode_blocked` (the register's G08 shorthand), with the ruling sheet's spelled forms — fired-and-replaced, fired-and-slot-empty, blocked-by-mode — documented as the prose names of the same three values; one enum, one alias note, never two competing vocabularies.

The model's stance is a separate, candidate-scoped **discriminated `intent`**: `{kind: enter}` carries **no reason field**; `{kind: wait, reason}` and `{kind: reject, reason}` **require** one of `insufficient_evidence | invalidated_setup | no_replacement | policy_block` (all four legal for both wait and reject). Intent is recorded beside the executable decision, which remains HOLD/SWAP unchanged; consistency is checked at validation — `wait` on a candidate coexists with HOLD absent a deterministic override, and a tick where a protective swap fired is never described as "no change" because the model intended to wait. Original model proposal, deterministic override, executed action, and failure `holdKind` stay separate recorded dimensions. The structured claim lands in the new field `structuredClaim`, never overloading the legacy `hypothesis` string that history rendering calls string methods on. Nested objects (claim, evidence refs, intent) get their own validation in P4 — the top-level validator does not recurse and is not claimed to. **Contribution-relative off guarantee (V11-01, V12-04):** the pilot and the call-record contract extend the *same* outgoing decision tool, so each arc's `off` removes exactly **its own contribution** with the other flags held fixed — pilot off strips the pilot's intent/claim fields whatever `CALL_RECORDS_MODE` adds, and only with **both arcs off** is the schema byte-identical to the pre-build baseline. Composition comes from the existing conditional schema builder, with the grouped composition rows carried in both contracts. The pilot's fields additionally appear only in an authorized pilot context — isolated advisory, or live behind the gate; the calls flag never enables pilot behavior. A P4 acceptance item.

**The composition rows (V13-03), governing both the outgoing tool and the capture record,** with `TICK_CAPTURE_ENABLED` and every other flag held fixed:

| Calls contribution | Pilot contribution | Resulting shape |
|---|---|---|
| off | off | the agreed pre-build shape (schema, prompt bytes, capture shape and version) |
| enabled | off | baseline plus the call/declaration fields |
| off | enabled in its authorized context | baseline plus the pilot fields |

Calls-off removes only the call and declaration capture paths; an enabled pilot's P5 fields keep their selectors, and the emitted capture schema and version continue to describe them. Each emitted capture shape names its registered schema version; revisions are allocated sequentially from the Phase 0 baseline of whichever package lands next. These rows define contract behavior, never permission to run the pilot outside its isolated and live gates.

## 8. Evidence joins (F05, F11, V11-02)

**8.1 Sealed inputs, before the decision.** Input identity is recorded at P3/P4 time, before setup evaluation and model dispatch: each required completed-bar fact is supplied with `{source, asOf}` or recorded `unknown` with abstention — no automatic extra retrieval, no post-hoc completion. Capture's request bytes remain the authority for what the model was shown; receipt enrichment keeps its `capture_refetch` label and is never attributed to the decision.

**8.2 The ref table.** Every reference names target, identity, cardinality, producer: `hypothesisRef` (§2.6 union; one per candidate action) → version record / frozen context, by the evaluation writer; `opportunityId` (one per candidate) → §4, at admission; `researchWorkId` (one per hypothesis version) → §3, at research completion; `setupEvaluatorVersion` + verdict record (one per candidate per tick) → §5, pre-dispatch; `callId` (per declaration) → the calls subcollection, by the call-record writer, minted only when `CALL_RECORDS_MODE ≠ off`, never invented, and minted only from a **durably committed evaluation identity** (V12-03) — `evalSeq` is not reserved at admission, so the call writer runs after the evaluation's commit (before capture finalization), create-once: a same-payload retry is legal, a conflicting duplicate is a typed failure, never an overwrite; the rule is the cockpit writer's, and P7's identity fixtures include the failed-before-evaluation-commit case. Multi-candidate ticks join each result to its candidate through these scoped refs; nothing tick-global that is candidate-scoped.

**8.3 Join states — identity and availability are separate facts (V11-02, V12-02; joint amendment).** `callId` is the call's **own minted identity and must not derive from `tickId`**; the check join uses `evalId`/`evalSeq`, which exist without capture. A minted **`tickId` is permanent**: capture-on mints it before the batch write, and retention deletes tick *bodies*, never the permanent tick record — so `tickId: null` appears only when none was minted (capture off). **Availability** is reported separately by the reader/projection, never baked into the identity: `off` (no tick minted) · `unresolved` (a lookup failed or the batch write timed out — cause **unknown** until resolved, per capture C-1; a timeout is never recorded as a proven failure) · `write_failed` (only on confirming evidence) · `body_expired` (permanent tick present, request bytes gone) · `complete`. **The literal wire shape, identical in both documents (V13-02):** `evidence: { tickId: string | null, availability: 'off' | 'unresolved' | 'write_failed' | 'body_expired' | 'complete', priceAsOf: string | null }` — `priceAsOf` is the committed evaluation's ISO-8601 `promptBuiltAt` in its source format at HEAD, derived display data, `null` when the source is missing, never the current time, and never an independent cutoff authority. **`complete` is necessary, not sufficient:** request bytes that are truncated, `copy_failed`, or otherwise not a usable pair (capture C-1's distinction) still exclude the call. A call whose request bytes are absent or incomplete, in any of these states, is **excluded from qualification-grade called-vs-happened evidence**, and the projection says which state it is in; absence is never recast as proof of what the model saw, and never grounds for a duplicate cutoff authority or an invented tick. Capture's allowlist, no-free-text rule, finalization position, and no-authority rule are preserved; schema bump, selectors, and serializer change together in P5's §2-reviewed writer extension.

**8.4 Film Room reader (P5 scope).** A bounded, owner-authorized join reader and server projection feeding the existing FilmRoomScreen: believed / called / done over retained fields, with honest `legacy | missing | expired | unavailable` states rendered as such. Subcollection access flows through the explicit projection, not widened client rules; raw learning receipts stay admin-only. Coordinates with the cockpit's call reader without depending on cockpit UI delivery.

## 9. Qualification (V11-01, V11-03; F01/F02/F03/F12/F13 retained)

**9.1 The isolation contract — access without authority.** The advisory harness (P7 — *built*, then run) executes the **full pilot path**: hypothesis consumption, the pilot prompt and conditional tool schema, intent mapping, the P6 verification seam, and **the real executor** — all pointed at an **isolated store** (injected database namespace) with the injected clock and data seams of §7, frozen market/data fixtures recorded under an input fingerprint, and **no production capability**: no production database handle, no production executor target, no side effects beyond the model call through the named adapter. The prohibition is on production authority, not on pilot behavior — the harness must run what it qualifies. Production serializers and validators are used unmodified. Comparison inputs are snapshotted once and fingerprinted; background writers (reflection, consolidation, batch review) never see the isolated store — which, with pilot outputs excluded from learning promotion, is the pilot's **comparison** freeze, owned by P7. Genuinely inert P1–P5 pieces (additive fields, the uncalled evaluator) may land on `main` before P6; every behavior-bearing live consumer sits behind the `live` gate; the parse-binding flip (§2.8) is its own founder-approved change.

**9.2 Mode write table.** `off`: nothing — the pilot's own contribution absent from schemas, prompts, and stores (contribution-relative per §6; only with every arc's flags off is the baseline byte-identical to today). `advisory`: isolated store only; an advisory equip never touches live agent settings; the harness exercises the P1 snapshot builder directly in isolated fixtures (necessary regardless — the production flat-six prescription deploys with no equipped watchlist, so that route is not claimed to transport the hypothesis); zero ordinary live writes, so off↔advisory rollback provably leaves live state untouched. `live`: ordinary paths, allowlist-gated per mode. Rollback honesty: leaving `live` stops new writes but does not undo written live records; nothing historical is recomputed.

**9.3 Preliminary vs final.** Runs before P6 lands are **preliminary** and cannot satisfy case E or final qualification. Final P7 exercises the real P6 validator and commit boundary against isolated state — all six caller shapes, changed-slot, finished-battle, duplicated acknowledgment, transaction retry — producing the deterministic-rejection *and* committed/unchanged post-state evidence case E requires.

**9.4 Case C prerequisite.** Full case C names the directive/grounding owner's accepted implementation and configuration as its prerequisite; the Speculator fixture is one regression case within it; P7 retains four distinct observations — user intent, committed canonical record or no-change, rendered response, downstream effect. No live semantic judge; D-24 untouched.

**9.5 A–I honesty and the live gates (V11-03).** The qualification report records per-case status; case F's external arm stays deferred pending Pi's negative control; case I is a gate, not a pass; founder acceptance of a report is acceptance of its stated limits, never evidence for an unimplemented case. **Live admission requires, per mode:** accepted case-I evidence for that mode; the evidence-corpus gates (capture deployed, TTL and coverage verified — flag-true is not data-ready); **and the freeze prerequisite** — that mode's frozen-input consumers named and qualified, with the handling of reflection/consolidation/batch-review outputs (including voice and subsequent deploys) demonstrated under case G so background changes cannot alter the active pilot contract. P7's isolated comparison freeze does not satisfy this live prerequisite; the allowlist stays empty until it is met. The R8 backed-week snapshot remains excluded with its own owner.
