### C. Scoring cadence

**Verdict: clear — the clock stays, the chip stays.** A rung banks only at a scoring check, never on a touch between checks; the check runs on the 15-minute cron with a market-hours gate and no sharding; "next check" is already computed client-side by a module the cockpit imports; the check reads the same provider endpoint as the modal's header at a different instant, and stores its price per held symbol as `evidence[SYM].px`. Scoring is not continuous.

**Does a rung bank only at a check? Yes (VERIFIED).** Legacy BaggerBomb: badge detection happens inside the check from that check's single quote — `calculateAssetScoreServer(asset, priceChange, thresholdHistory[sym], {}, thresholdPriceChange)` (`agent-evaluate.js:1307-1313`) is called with empty extremes, so the high-water mark is `max(historyMax, multiplier)` (`agentScoring.js:275-283`); a touch between checks is never seen. The mark persists as `thresholdHistory.{SYM}` each check (`:1454`), so a rung reached at a check stays for the day; the durable bank is the nightly daily-scores cron (`45 1 * * 2-6`, `agent-daily-scores.js:4`), which increments `bankedBadgePoints` (`:198-203`). The measured model (v2) is the same by construction: `high = max(h.high, quote.price)` on the check's quote, `crossedTiers = targets.filter(high >= target)` (`stockThresholdModel.js:71-74`), and the comment says why — "Whole-session high/low values do not prove when a level was touched and therefore cannot grant a lifetime badge" (`:58-59`). The per-minute `intraday-poll` writes only the intraday store (§D); the settle run (`0 2 * * 2-6`) is the expiry sweep "and nothing else" (`agent-evaluate.js:288-291`); `compute-daily-baggerbomb-levels` and `baggerbomb-v4-daily-scores` write `battles/`, the V4 collection, not `agentBattles` (`compute-daily-baggerbomb-levels.js:288`, `:348-349`). **So the next-check clock is a real deadline and the design's "points bank at the scoring check" is true.**

**Which cron, which minutes, sharding (VERIFIED).** `/api/cron/agent-evaluate` at `*/15 13,14,15,16,17,18,19,20,21 * * 1-5` UTC (`vercel.json:157-158`). The handler's gate is `isMarketOpen()` (`agent-evaluate.js:443-445`; `marketSchedule.js:130-147`: weekend, holiday, early close, `openMinutes ≤ m < closeMinutes` in ET via `Intl`), with no minute-mark gate, so the eligible firings are :00/:15/:30/:45 from 9:30 to 15:45 ET in both EDT and EST (13:30–19:45 UTC in EDT, 14:30–20:45 UTC in EST; the 4:00 PM slot is excluded by `<`), and 12:45 ET on an early-close day; the other firings return `market_closed`. **No sharding**: battles are processed sequentially, ordered by `lastEvalStartedAt`, under a 290-second budget (`:232`, `:497-502`), with the tail deferred to the next slot (a `check_deferred` beat; REPORTED subagent) — so one battle's next check can slip a slot. A battle is dormant before its first trading day and skipped on an unusable quote (REPORTED, subagent).

**Can "next check" be computed client-side? It already is (VERIFIED).** `api/_utils/callRecords/horizon.js` carries the schedule as data (`EVALUATOR_SCHEDULE`, `EVALUATOR_SLOTS`, `:24-34`), `eligibleSlotsOn(etDate)` from `getSessionForDate` (`:68-69`) and `nextEligibleSlot(afterMs, { battleExpiresAtMs })` (`:92`), and the cockpit's client model imports it (`cockpitModel.js:42`). Its header rule: "Never `lastCheckedAt + interval`; a skipped slot is the sweep's to catch" (`:15`). A second derivation exists in the Desk adapter, `deriveDueAt(lastCheckedAt) = last + 15 min` (`baggerbombAdapter.js:360-364`) — two "next check" clocks already coexist, and Build A's clock must use the first (a §9 hazard for a third). The calendar is client-importable (`src/utils/marketCalendar.js`, maintained for 2026–2027). The clock's honest caveats: the slot is when the cron *fires*; a battle late in the queue is checked up to a few minutes later; a check that builds no prompt leaves no entry.

**Which price does the check read (VERIFIED).** `getStockAnalysisData(symbol, { forceRefresh: true, fields: ['daily', 'price'] })` (`agent-evaluate.js:1184-1186`) → EODHD `/real-time/{sym}` with `close || previousClose` (`marketDataCache.js:794-799`; a stand-in is flagged `previousCloseStandIn`, `:818`). **How banked state is recorded (VERIFIED, §B).** Legacy: `thresholdHistory.{SYM}` every check, `scoreState.bankedBadgePoints` nightly, `trades[].lockedPoints` on a close. Measured: `scoring.stockRewardHistory.{side}.{positionId}` (`high, low, observedAt, crossedTiers`) and `scoring.stockRewardContexts` (REPORTED, subagent; the receipt itself is on the position, §B). `dailyLevels` is a **V4-only** record: `battles/{id}.state.dailyLevels = { date, computedAt, assets { SYM { baseline, baggerBomb, doubleBagger, tenBagger, bust, crash, meltdown, threshold } } }` (`compute-daily-baggerbomb-levels.js:348-349`; shape REPORTED subagent) — no writer on `agentBattles`, so the Bomb tab's `cronLevels` is always null in an agent battle and Bomb mode's ladder comes from the receipt (measured) or `swapPrice × baseATR` (legacy), not from `dailyLevels`.
