## 1. Why this review, and how it was run

BUILD_RULES §2 makes review mandatory at ≥10 files **or** ≥1500 lines. The spec's own PR 0 row (`FANTASYTRADES_BACKING_BETA_SPEC_V1_3.md` §12) prescribes twelve files once each module carries its test — the flag, the pin-guard entry, the pin suite, the constants and their test, the helper and its test, the endpoint with a lit and a dark suite, the rules block and its emulator suite — and the deny-by-default protected-store scanner forced a thirteenth (its allowlist: every transaction-handle write reads as `unresolved` by construction, the `research.js` precedent), so the branch crossed the threshold on file count alone (13 / 1,125). The spec flagged PR 2 and PR 4 for this review; the file arithmetic puts PR 0 there too, so it was run rather than waived.

`/code-review` is not a skill in this environment, so the mandate was met with a **4-lens adversarial review** on isolated snapshot trees — one `git archive` extraction per reviewer under the session scratchpad, `node_modules` symlinked, read-only on git and on the shared working tree; the mutating lens ran last on its own tree with the emulator on its own ports (the Sep 2, 2026 reviewer-isolation ruling):

- **A — domain correctness and spec conformance:** the pipeline against the brief's numbered steps and spec §12 PR 0, the §6 doc shape, transaction semantics under the real Admin SDK, the helper contract, the constants, scope, header honesty, the §4 import rule.
- **B — wiring, lifecycle and the dark-merge guarantee:** every importer of the new modules, module-scope side effects, the 16 bare-factory `featureFlags` mocks, the flag-pin guard mechanics with an empirical flip walk (both halves of the FLIP MAP), Vercel deploy behaviour of the dark route with the real middleware (OPTIONS / GET / anonymous POST / authenticated POST), CI collection, the scanner allowlist against the scanner's code, the cron budget, twelve `api/`-walking census suites.
- **C — security and Firestore rules:** rules semantics including get vs list and the deny-all catch-all, the emulator suite's integrity (`assertFails` requires PERMISSION_DENIED in `@firebase/rules-unit-testing` 5.0.1, so no row can pass for a non-rules reason), positive controls, the auth-before-flag oracle (anonymous callers get identical bodies and headers dark vs lit), body handling incl. prototype-shaped keys, identity binding, race correctness.
- **D — test integrity, mutating:** a 22-defect matrix plus two extras across the endpoint, helper, constants, flag/guard, dark-suite structural rows and the rules (5 emulator runs), each defect applied by exact-once patch, run, restored and sha256-verified.

Every finding was then handed to an independent refuter on its own extraction and instructed to **refute** it with a concrete repro (R1: lenses A and C; R2: lens B; R3: lens D). The coordinator additionally mutation-checked each test fix it authored (F-A1's importer walk against the sibling spelling; F-C1's list rows against a deliberately widened rules text through the suites' own `COMPOSITION_RULES_TEXT_PATH` knob; F-B1's tripwire with the flag forced true; F-D1's count row with an unrelated-name accessor). Seven reviewer runs completed; two launches were lost to a session rate limit and re-run on fresh trees — no reviewer ever shared a tree, and none touched the working tree or git.

**Verdict: 8 findings raised (A 1 + 1 shared with C, B 1, C 3 + the shared one, D 2), 8 CONFIRMED by the refuters — four of them narrowed or reclassified — 0 REFUTED outright, 1 sub-claim REFUTED (the "invalidates stale clients" docstring reading). No critical, no high, no medium code defect, no live functional bug. Five findings fixed in-branch, all test- or comment-only; three recorded as notes for PR 2 and the founder. The flag-off surface is byte-identical and the route is unreachable while dark.**

Two refutations are worth recording because they show the review pushing back on itself:
- **F-C1 was narrowed:** an in-tree get/list split of the rule IS caught by the dark suite's static rules-text pin; what the emulator suite could not see was the same split in the LIVE ruleset (its stated purpose via `COMPOSITION_RULES_TEXT_PATH`). The three list rows added close exactly that gap and were proved to fire (the original suite stayed 12/12 green against the widened text; the amended suite reds on both denial rows).
- **F-A2/F-C2's docstring sub-claim was refuted on the literal text:** "invalidates stale clients" is what a `TERMS_VERSION` bump does (a client sending the old string gets 400). The reword that shipped is a clarification, not a correction; the substantive half — existence-only eligibility, no re-attestation path after a terms revision — is spec-conformant (§12: "an existing doc is returned unchanged") and is recorded as the pre-flip decision the spec already assigns to counsel (§8, §11 gate 1).
