## 3. The rulings as applied, and the builder's interpretations

- **R-S5-1 · the Loadout, from the owner's agent document.**
  - *Source.* `hub.agent` and `hub.agentLoading` are App's `primaryAgent` and `agentLoading`, the `useAgent` hook's legacy fields (src/App.jsx:8711). `useAgent` is not touched. The shells' own hook reads the same agent (starting check, last row).
  - *States.* `deriveLoadout` (hub/selectors/loadout.js:143): `loading` until the agent resolves; `none` when it resolved to no agent, which reads spec §3's "Create your agent first"; otherwise `ready`. A ready Loadout's cards carry their own states, so a slow lists read never hides the archetype. The hook has no error channel, so a failed subscription also resolves to no agent: the line is honest about absence, not about the cause (and App's onboarding gate keeps a signed-in player with no agent off the dashboard, so the state is reachable today only in App's degraded signed-out case; S3's error channel must split it into "Agent unavailable · Retry" and absence).
  - *Archetype.* The name and the approach come through `archetypeLines` (hub/archetypeLines.js:27): `getArchetypeDisplayName(code)` and, for a code in the identity table only, `getArchetypeIdentity(code).disposition`. That file is the hub's one importer of the legacy archetype tables (§10.2, Q-S5-9). One difference from the shells, on purpose: `getArchetypeIdentity` falls back to the analyst's profile for an unknown code, so the shells would print the analyst's disposition under the name "Unknown"; the hub prints an approach only for a code the identity table holds.
  - *Watchlist.* `useHubLoadout` (hub/useHubLoadout.js:53) calls the shipped `listWatchlists()` once, when an agent has resolved (so once per mount of the hub), and again on `refresh()` or Retry. `closeSheet` (hub/useHubRuntime.js:92) calls `refresh()` when the watchlist sheet closes: after an equip, an unequip, or a close with no choice. Coming back from the Forge remounts the hub, and that is the mount read. There is no timer, focus listener or poll; the mount guard plants one of each against the file and expects them to be caught. A refresh that fails keeps the lists already held. Every result carries the owner it was read for (`ownerKey`), and another owner's lists are dropped in the same render that brings the new agent (spec §3). **An equip made elsewhere** (another tab or device, arriving through the agent subscription) can name a list committed after this hub read its lists. Each settled read records the equipped id it was issued under (`readFor`). The lists are read once more only when the id now equipped is neither among them nor the one they were read for, so a list that was already gone at mount is answered by the mount read and never read for twice; the card reads "checking" until that read answers, and a failed read for it is the error state with Retry, never "unavailable" (review E4-2).
  - *Adjustments.* `getTraitSlotSummary(agent)`, drawn only where `getEquipSlots(agent)` has the `traits` slot. `TRAIT_SLOT_ENABLED` is false (src/config/featureFlags.js:118), so today the adjustments card, its sheet and its Forge door draw nowhere, in the hub or in the shells. They are built and tested, and they are not on the smoke build (§12). Their summary strings come from the shipped helper and sit outside the copy guard, like the archetype name and approach (E4-6, by ruling).
  - *Locked.* One predicate, `equipLockOf` (hub/selectors/loadout.js:116), drives the "Locked in battle · …" line and every picker (BUILD_RULES §9: a label and its source cannot disagree). It is the union of the shells' two expressions of the same lock: `deriveDeployGate(...).equipLocked`, which the shells label with, and `Boolean(agent.activeBattleId)`, which they disable their slots by. With `CASUAL_CLONE_CONCURRENCY_ENABLED = true`, as shipped, `equipLocked` is that agent field and the two agree. While locked, the three pickers are not offered. The Forge doors stay: the Forge browses and builds, and a game keeps the loadout it was deployed with.
  - *Interpretation, "after a return from the Forge or a sheet".* Only the watchlist sheet can change the equipped list, so only its close re-reads the lists. Closing the record, archetype or traits sheet does not, and a row pins both halves. The literal reading, a re-read after every sheet, is one condition removed in `closeSheet`.
- **R-S5-2 · the idea-first labels.** `ideaLabelKind` (hub/selectors/loadout.js:42). The records flag dominates, read through its accessor `isHypothesisRecordsOn()` as featureFlags.js prescribes: off, the label is the neutral "N names" even when the list carries a positive pointer (with the records dark, a stale pointer would name an idea the player cannot see). On, an absent or null pointer reads "Plain watchlist · no idea yet" and a positive integer reads "Universe · N names". Anything else (0, a negative, a fraction, a string, NaN) is malformed and reads neutral, which is the server's own rule (`currentVersionOf`, starting check). N is the number of names the card draws, each once (`symbolsOf`, hub/selectors/loadout.js:54), and the watchlist sheet's rows count with the same function. The card shows the label only for a resolved list, and never an idea's statement or status. Q-S5-4 puts two questions about these labels to the founder.
- **R-S5-3 · career.** `deriveCareer` (hub/selectors/loadout.js:173) returns `${wins}W-${losses}L` from `agent.stats.wins` and `.losses` only when both are non-negative safe integers. Anything else reads `unavailable`, never zeros, and the History sheet then says "Career record unavailable" (spec §7: "show unavailable rather than synthesize totals"). `useAgent`'s own `record` string is deliberately not used: it prints "0-0" for a missing stats object and "undefinedW-…" for a partial one. The caption is S1's `COPY.history.careerCaption`, "career · BaggerBomb vs CPU · as recorded". Draws and win rate are not in the data. **The record is displayed only inside the History sheet, and the hub opens that sheet only when `sections.games` holds a completed game, which is S3's data.** S5 supplies the value and proves it by row; the smoke build cannot show it (§12). The "unavailable" line is a four-line addition to `HistorySheet.jsx`, a file S3 will also touch (Q-S5-10).

- **R-S5-5 · the Forge bridge.** `onOpenForge` (src/App.jsx:8706) sets the Forge's first area, when the request names a valid one, and `setShowForge(true)` in the same handler. `forgeAreaOf` (hubChrome.js:57) returns the area, or `watchlists` for a request that names only a `watchlistId`, or `null`. `ForgeWorkshop` reads `initialArea` once, in its `useState` initializer (`ForgeWorkshop.jsx:74-75`), so the view is set before it mounts. A request with no valid area is exactly the bare `setShowForge(true)` of every other Forge open: a mount-guard row pins the source text and the three callers of `setForgeInitialView`, and `hubForgeTargets.jsdom.test.jsx` runs App's three Forge statements (quoted from App.jsx by a row) against the real `ForgeWorkshop` for every open, plain and StrictMode.

The hub names its adjustments door by the same flag, so a label never opens another tab (the Forge also honours a dev-only `?release3Character=1` URL parameter that the hub's label does not read: N-S5-5).

The doors are therefore "Forge Lists" and "Forge Character" / "Forge Traits", and no action says "Edit <list>". The watchlist editor is the one exception to "closing the Forge shows the screen under it", and it is today's: its close sets the screen to `home` and reopens the Forge on Lists (src/App.jsx:10003), so Lists → editor → close the Forge ends on home, exactly as from the shells' "Create a watchlist in Forge" (N-S5-1).
  - *Contract.* The bridge sets the area only while the Forge is closed *in practice*: the hub is unmounted while the Forge shows, and every caller is a gesture handler. A call made while the Forge is already open would leave its area for the next open. A one-token guard was tried and taken out again (it fixed a fresh-closure call and not a stale one); the precondition is written in `useHubRuntime`'s header where S2b and S3 read it (review E1-3).
- **R-S5-6 · one overlay stack.** `createOverlayStack` (hub/overlayStack.js:108) is plain DOM; `HubOverlayProvider` (hub/HubOverlays.jsx:24) gives one stack per hub to React. Every overlay registers. `HubSheet` registers itself when it mounts, with `keep` (its own root). `useHubSheets` registers the four shipped sheets in the click handler that opens them, `within` the hub (hub/useHubSheets.js:69).
  - *Why `within`, not "every body child" (review E3-1 and E2-1, two lenses, MAJOR).* The shipped sheets portal into `<body>` and keep their DOM there while they animate out (0.3–0.43 s). A sheet re-opened inside that window re-uses that node, and marking every body child at registration marked the very sheet being opened; the page was left with nothing interactive, and nothing in the sheets can get it back (they have no Escape). A keyboard, switch or assistive-technology user can trigger it, because the stack itself returns focus to the opener when the sheet closes (and Enter auto-repeat can fire a second click there); a pointer cannot, because the exiting backdrop covers the viewport. The stack therefore marks only the app root the hub sits in, plus the roots of any overlay beneath it that registered with `keep`. The refuter of E3 also weighed keying each sheet per open (as `TraitsSheet` already is) and ignoring a re-open while the exit runs; it chose the key, and I kept `within` because a registration API that forces the choice cannot be forgotten by S2b the way a key can, and it changes no sheet's lifecycle. The real-sheet rows (`CommandCenterHub.realSheets.jsdom.test.jsx`) run the sequence on `EquipSheet`, `ArchetypePicker` and `AgentRecordSheet`, both docks.
  - *The engine* `inertSiblings` (hub/overlayStack.js:60) is reference-counted: each call holds every element it marks, and an element comes out of inert only when the last holder lets go, which is the repair of S1 review L3-12 (two sheets closed out of order un-inerted `#root` while the second was open).
  - *Focus.* Focus goes to each overlay's opener. An overlay closed out of order hands its opener on to the one above and gets it back when that closes, and the owed openers survive an intermediate close. If an overlay closes onto an opener that cannot take focus and another is still open, focus goes into that one (its dialog). If the whole hub is replaced under an open overlay (a site flip remounts the hub under the gate's desktop frame; the Forge opening replaces it), the provider's unmount frees the background and, when focus has fallen to `<body>` and a new hub shell exists, hands it focus; a live focus is left alone (E3-2).
  - *`modalOpen`* has three exposures: the context hook `useHubModalOpen()`, the `data-hub-modal-open` attribute on the hub root, and the stack's `modalOpen` getter. Rows keep them equal at every step, `releaseAll` included (E3-3). jsdom has no real `inert` focus semantics, so the focus rows blur the opener to simulate what a browser does; the browser behaviour of the four shipped sheets was measured separately (§7).
  - *Contract for S2b* (written in the stack's header): register an overlay whose root you can name with `keep`, and one you cannot (the shipped `EquipSheet` family, `ScoutingBoardSheet` included) with `within`; an overlay registered with neither has no root the stack can name; render overlays inside the hub's provider, or they are invisible to `modalOpen`.
- **R-S5-7 · the bug button and the season banner.** `hubOwnsDashboard` (hubChrome.js:49) is `hubOn === true && screen === 'dashboard' && !showForge && hubFailed !== true`, computed once in App (src/App.jsx:8715). The ClashBot button's existing `hidden` gained `|| hubOwnsScreen` and the banner's chain gained `&& !hubOwnsScreen`; the widget stays mounted, so its open event is still heard.
