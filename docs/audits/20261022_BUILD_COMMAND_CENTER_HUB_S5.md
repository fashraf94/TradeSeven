## 3. The rulings as applied, and the builder's interpretations

- **R-S5-1 · the Loadout, from the owner's agent document.**
  - *Source.* `hub.agent` and `hub.agentLoading` are App's `primaryAgent` and `agentLoading`, the `useAgent` hook's legacy fields (src/App.jsx:8711). `useAgent` is not touched. The shells' own hook reads the same agent (starting check, last row).
  - *States.* `deriveLoadout` (hub/selectors/loadout.js:158): `loading` until the agent resolves; `none` when it resolved to no agent, which reads spec §3's "Create your agent first"; otherwise `ready`. A ready Loadout's cards carry their own states, so a slow lists read never hides the archetype. The hook has no error channel, so a failed subscription also resolves to no agent: the line is honest about absence, not about the cause (and App's onboarding gate keeps a signed-in player with no agent off the dashboard, so the state is reachable today only in App's degraded signed-out case; S3's error channel must split it into "Agent unavailable · Retry" and absence).
  - *Archetype.* The name and the approach come through `archetypeLines` (hub/archetypeLines.js:27): `getArchetypeDisplayName(code)` and, for a code in the identity table only, `getArchetypeIdentity(code).disposition`. That file is the hub's one importer of the legacy archetype tables (§10.2, Q-S5-9). One difference from the shells, on purpose: `getArchetypeIdentity` falls back to the analyst's profile for an unknown code, so the shells would print the analyst's disposition under the name "Unknown"; the hub prints an approach only for a code the identity table holds.
  - *Watchlist.* `useHubLoadout` (hub/useHubLoadout.js:53) calls the shipped `listWatchlists()` once, when an agent has resolved (so once per mount of the hub), and again on `refresh()` or Retry. `closeSheet` (hub/useHubRuntime.js:105) calls `refresh()` when the watchlist sheet closes: after an equip, an unequip, or a close with no choice. Coming back from the Forge remounts the hub, and that is the mount read. There is no timer, focus listener or poll; the mount guard plants one of each against the file and expects them to be caught. A refresh that fails keeps the lists already held. Every result carries the owner it was read for (`ownerKey`), and another owner's lists are dropped in the same render that brings the new agent (spec §3). **An equip made elsewhere** (another tab or device, arriving through the agent subscription) can name a list committed after this hub read its lists. Each settled read records the equipped id it was issued under (`readFor`). The lists are read once more only when the id now equipped is neither among them nor the one they were read for, so a list that was already gone at mount is answered by the mount read and never read for twice; the card reads "checking" until that read answers, and a failed read for it is the error state with Retry, never "unavailable" (review E4-2).
  - *Adjustments.* `getTraitSlotSummary(agent)`, drawn only where `getEquipSlots(agent)` has the `traits` slot. `TRAIT_SLOT_ENABLED` is false (src/config/featureFlags.js:118), so today the adjustments card, its sheet and its Forge door draw nowhere, in the hub or in the shells. They are built and tested, and they are not on the smoke build (§12). Their summary strings come from the shipped helper and sit outside the copy guard, like the archetype name and approach (E4-6, by ruling).
  - *Locked.* One predicate, `equipLockOf` (hub/selectors/loadout.js:130), drives the "Locked in battle · …" line and every picker (BUILD_RULES §9: a label and its source cannot disagree). It is the union of the shells' two expressions of the same lock: `deriveDeployGate(...).equipLocked`, which the shells label with, and `Boolean(agent.activeBattleId)`, which they disable their slots by. With `CASUAL_CLONE_CONCURRENCY_ENABLED = true`, as shipped, `equipLocked` is that agent field and the two agree. While locked, the three pickers are not offered. The Forge doors stay: the Forge browses and builds, and a game keeps the loadout it was deployed with.
  - *Interpretation, "after a return from the Forge or a sheet".* Only the watchlist sheet can change the equipped list, so only its close re-reads the lists. Closing the record, archetype or traits sheet does not, and a row pins both halves. The literal reading, a re-read after every sheet, is one condition removed in `closeSheet`.
- **R-S5-2 · the idea-first labels, as narrowed by the founder's ruling Q-S5-4a.** `ideaLabelKind` (hub/selectors/loadout.js:56) takes an explicit `ideaAccess` (hub/selectors/loadout.js:30: `'unknown'`, `'admitted'` or `'not_admitted'`; anything else reads `'unknown'`, hub/selectors/loadout.js:33). **Only `'admitted'` shows a label.** S5 cannot know whether the server admits a player to idea records (the client "never learns who is admitted", `featureFlags.js`), so S5 passes none: the access is `'unknown'` and **every player reads the neutral "N names"**. Slice S6 supplies `hub.ideaAccess` from its gated reader (the runtime reads it through the normalizer: hub/useHubRuntime.js:90); a copy-guard row fails any hub source that writes the word "admitted" outside the selector, and App carries no `ideaAccess` key. For an admitted player the first S5 logic stands: the records flag dominates, read through its accessor `isHypothesisRecordsOn()` as featureFlags.js prescribes: off, the label is the neutral "N names" even when the list carries a positive pointer (with the records dark, a stale pointer would name an idea the player cannot see). On, an absent or null pointer reads "Plain watchlist · no idea yet" and a positive integer reads "Universe · N names". Anything else (0, a negative, a fraction, a string, NaN) is malformed and reads neutral, which is the server's own rule (`currentVersionOf`, starting check). The card shows the label only for a resolved list, and never an idea's statement or status.
