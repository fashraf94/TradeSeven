### Refuted candidates, by lens (the reasoning is in each lens's report; the load-bearing ones restated)

- **Lens A (7 refuted).** A synchronous throw, a non-function settler and an `undefined` return are all inside the inner try and counted on `settlementErrors`, marker set. `summary.backing` never reaches `markerSummary`, the state doc or `isDutySatisfied`; a dark run's summary, read log, write log and whole store `toEqual` a hook-stripped copy of the module. Budget: quantified above. `voidGroup` racing the loop or the settlement: `COMPLETE` is terminal, both transitions re-assert on fresh reads, and every interleaving yields either "voided, never paid" or "paid, never voided". No double-run (the in-transaction status gate; a second duty run loses at the transition before reaching the hook). No `tournament*` write after the transition in any run.
- **Lens B (10 refuted).** Every §3 number re-derived by hand matches; the D-j tie set is strict `===` on stored composites over `groupMembers` through the clamped reader; the unbacked winner loses everything with no refund entry and the `no_winner` abort is the right disposition (corruption-only, writes nothing); the predicate is four parts on the in-transaction read; §B7.2 is applied to every settled stake with the ladder's month key and voided stakes are never read; the D-ae test reads the same clamped entry `getWeeklyComposite` reads; the ceiling arithmetic is 3/5 (+1 pool) with prior 2/4; the §6 field set is complete; the "not in this PR" list holds; idempotency converges from every interruption point.
- **Lens C (9 refuted).** The duty is byte-identical while dark (the one ungated addition is a local object); the new import edge has no module-scope side effect (env proxy + console patch probe, ~30 ms); every flag read is at call time inside the gating function; no fenced file is touched and `backingSettlement.js → tournamentLeaderboard.js` is transitive, not a §2.3 direct importer (`tournamentLeaderboard.js`'s header claims a fenced import it does not have — pre-existing prose); the scanner registers exactly three `tx.set` sites and no `call:settlePool` site, and inlining a `db.collection()` chain in a write argument would register the helper and red the scan (the allowlist note's claim, verified); `now` as an ISO string and the `'friday_duty'` literal are handled; Vercel file-based routing needs no `vercel.json` change; the hook test's `vi.mock` reaches the orchestrator path; a fourth importer or a flag read in the primitive reds the pin rows.
- **Lens D (8 refuted).** The H1 row reds under `summary.errors++` without rethrow; the H2 rows red under `tx.update`, a `tournamentRanks` write and a post-transaction `groupRef.update`; the projection row reds when winners are miscounted; the H4 row reds when the status clause comes from the cheap read; the H5 row correctly depends on the transactional gate (removing the cheap gate alone is not a defect; removing the transactional one, or gating on the cheap pool, reds it); the net-BP row reds when `recordStakeLoss` is skipped for losers; the SDK-retry row reds without a real conflict; every fixture number re-derived matches. (Noted: the careerNet half of the net-BP row cannot fail under a `recordStakeLoss` defect by construction — the season half carries it.)
- **Lens E (15 refuted).** Header/Bearer-only secret and the 405 → 401 → 404 → body → 409 → reads order; crafted ids reach the backend's own INVALID_ARGUMENT as a generic 500 with nothing written; internal messages are never echoed and `err.code` is a fixed vocabulary; no secret in any log line; `maxDuration: 60` fits the worst case; no read after any write (SDK-enforced, row-pinned); only the two hold arms return after a write and that write is the whole intended state; the wallet threading survives the SDK's transaction-object reuse because every wallet is re-read per attempt; `tx.get(query)` is supported and the read set (every stake of the pod) contends only with a concurrent close or admin void; the SDK counts writes per operation with no same-document coalescing, exactly as the projection assumes (120 losing = 361, 120 winning = 601 → hold, 95/96 winners is the boundary); the single-equality stake query needs no composite and PR 2's `(groupId, status)` is still `closePool`'s; `ownerId` is the seat's odUserId on a tournament battle (fenced service, read only) and CPU seats resolve an agentId with a null hash; an `isDev` flip between reads is unreachable and fails safe (`no_pool`); the rules need no change (`private/*` unreadable, settled stakes keep `userId`); settle-on-read cannot be abused because it is unreachable (finding 1).
