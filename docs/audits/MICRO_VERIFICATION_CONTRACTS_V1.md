## Q3 — the `evaluatingAt` lease in `agent-evaluate.js`

> Adversarially re-verified: every load-bearing claim CONFIRMED, including the three attack targets (stale-writer clobber, lease-vs-maxDuration, release nulling another owner's lock).

**1. Acquire logic — transactional read-then-conditional-write.** `api/cron/agent-evaluate.js:544-578`:
```js
const lockAcquired = await db.runTransaction(async (transaction) => {
  const doc = await transaction.get(battleRef);                 // :545
  const data = doc.data();
  const currentLock = data?.cronState?.evaluatingAt;            // :547
  if (currentLock) {
    const lockAge = Date.now() - new Date(currentLock).getTime(); // :550
    if (lockAge < EVALUATING_LOCK_TIMEOUT_MS) return false;      // :551 held → skip
  }
  transaction.update(battleRef, {
    'cronState.evaluatingAt': new Date().toISOString(),          // :575 claim/steal
  });
  return true;
});
```
If `currentLock` is truthy and `lockAge < 120_000 ms` it returns `false` and the caller skips (`:580-584`, `summary.skipped++`). If the lock is absent or `lockAge >= 120_000`, control falls through and the lock is claimed **or stolen**. Firestore optimistic concurrency makes the check-and-set atomic (a concurrent commit to `battleRef` retries the transaction), so two invocations cannot both see an empty/stale lock and both claim.

**2. Owner identity — TIMESTAMP-ONLY.** The written value is `new Date().toISOString()` (`:575`) — a bare ISO wall-clock string. **No owner identity: no worker ID, no invocation/nonce, no fencing token.** The lease records only *when* it was taken, not *who* took it — so no release site can verify it owns the lease it clears.

**3. Release — every site, on success AND error.** The lease is released by writing `'cronState.evaluatingAt': null`:
- **Success / normal flush:** `finalizeCronState(finalUpdate, …)` (`:2711`) sets it, then plain `battleRef.update(finalUpdate)` (`:2740`).
- **Five in-tick early-return flushes** (skip-Haiku, proposal-pending, gameplan, score flush): `finalizeCronState(scoreUpdate)` at `:895/:1785/:1797/:1826/:1903` then `battleRef.update(scoreUpdate)` at `:907/:1788/:1800/:1829/:1908`.
- **Degraded-quotes early return:** `:726` `battleRef.update({ 'cronState.evaluatingAt': null }).catch(()=>{})`.
- **In-`try` catch (error path):** `:2743-2745` `battleRef.update({ 'cronState.evaluatingAt': null }).catch(()=>{}); throw err;`.
- **Outer per-battle catch:** `:351-354` `battleRef.update({ 'cronState.cronErrors': …, 'cronState.evaluatingAt': null })`.
- **`completeBattle` terminal transaction:** `updatePayload` includes `'cronState.evaluatingAt': null` (`:3855`), committed at `:3911`.

`finalizeCronState` (`api/_utils/agentCronState.js:35-49`) sets it **unconditionally** — `update['cronState.evaluatingAt'] = null; // always release the evaluating lock` (`:37`). The `finally` block (`:2746+`) does **not** touch the lock (only dispatches narrations). **If the process dies mid-hold** (crash/OOM/timeout-kill, no catch runs) the lease is not released — it **ages out passively after 120 s** (`:551`), during which the battle is skipped (`:580-584`). The degraded-quotes comment confirms the intent (`:724-725`).

**4. Stale-writer trace — the race is real and unprevented.** A acquires at T0 (`:575`); A over-runs past 120 s (legitimately — it is allowed 300 s, see below). At T0+121 s, B's acquire transaction sees `lockAge >= 120_000` (`:551` false), falls through, and claims a fresh lease. Then A finishes and reaches its flush:
- **Does anything prevent A's write?** **No.** A's terminal write is `await battleRef.update(finalUpdate)` (`:2740`) — a **plain, non-transactional `update()` with no precondition**: it does not re-read `evaluatingAt`, does not compare timestamps, and has no owner to check (§2). A writes unconditionally.
- **Does A's release null out B's lease?** **Yes.** `finalUpdate` was stamped by `finalizeCronState` (`:2711` → `agentCronState.js:37`), so A's `:2740` write sets `evaluatingAt` to `null`, **clobbering B's live lease** — a third worker can then acquire immediately.
- **Do A's data writes carry a fencing precondition?** **No.** `finalUpdate` (and the `scoreUpdate` early-return variants at `:907/:1788/:1800/:1829/:1908`) are plain `battleRef.update(...)` calls — no `evaluatingAt`-equals precondition, no transaction, no fencing token. A's `scoreState`, swaps, `statusFeed`, `vwapTicks`, etc. are **last-writer-wins**, overwriting whatever B committed. (The ledger swap path `confirmSwap` is separately transactional on the *ledger* doc, but the battle-doc `finalUpdate` itself is unfenced.)

**Concrete outcome:** A's write succeeds unconditionally, overwrites B's battle-doc state, and nulls B's lease — mutual exclusion collapses. The only guard against A and B overlapping in the first place is the 120 s age threshold; once A exceeds it there is zero protection.

**5. Lease duration vs `maxDuration` — the lease is the *smaller* one.** `export const config = { maxDuration: 300 }` (`:122`, 300 s), `EVALUATING_LOCK_TIMEOUT_MS = 120_000` (`:125`, 120 s), soft `TIME_BUDGET_MS = 290_000` (`:126`). **`maxDuration` (300 s) is 2.5× the lease timeout (120 s).** A single `processAgentBattle` is permitted to run to 300 s, so a *non-crashed, legitimately-running* worker holding the lease past 120 s becomes stealable — a **180 s-wide collision window every invocation**, producing exactly the §4 stale-writer collision without any crash. The comment at `:117-121` records that `maxDuration` was widened 60→300 without touching the lease constant. *(A stale comment at `:2757-2758` still references a "60s maxDuration" — comment only, not behavior; flagged per the read-the-implementation rule.)*

**6. Used elsewhere? Other locking primitives.** This exact timestamp-only lease (single field on the doc, timestamp value, age-based steal, unfenced release) is unique to `evaluatingAt`. The repo's other primitives are **stronger** — owner-identified and same-doc read+write inside one transaction:
- **`reserveSymbol` (`api/_utils/tournamentAgentLedger.js:364-410`):** same-txn `tx.get(ref)` (`:370`) → `tx.set(ref,…)` (`:407`); records an **owner** `reservations[symbol] = { by: agentId, battleId, at }` (`:406`); ownership-checked (`heldEntry.heldBy === agentId`, `:379`; `resv.by !== agentId`, `:385`); longer TTL `RESERVATION_TTL_MS = 10*60*1000` (`:67`) with a **hardening cross-doc read** of the rival's battle before stealing a stale reservation (`:390-402`) — no such safety in the lease steal.
- **`tournamentClaims.js:104-290`:** a single `runTransaction` (`:117`) reading group+ledger docs, all mutations keyed by `claimId` (owner-identified), same-doc read+write.
- **`canonicalOpen.js:107-124`:** transactional **idempotent conditional write** — `tx.get` (`:113`), writes only keys not already present (`:115-124`); owner-less but the write is conditioned on current doc state (unlike the lease's blind `update`).
- Note `completeBattle` (`:3733`) is fully transactional with a status precondition (`fresh.status !== 'active'` → abort, `:3741`), but it **nulls `evaluatingAt` (`:3855`) without ever reading or holding the eval lease**, from a separate expired-battles loop (`:210-241`).

Realized vs unrealized P&L.** **Unrealized** = `returnSinceEntry` recomputed at `:275` (`((freshPrice - entryPrice)/entryPrice)*100`, percent, against average basis), stored per-position. **Realized** is *not* stored as a dollar field: a full SELL computes a percentage `returnSinceEntry` at `:42` and attaches it to the SELL trade (`:50`); a dollar figure is derived only later in `computeTradeStats` (`seasonLeaderboard.js:376`: `dollar = (t.value ?? 0) * (t.returnSinceEntry/100)`) — and it uses `trade.value` (exit **proceeds** `shares*price`, `:41`), **not** cost basis, so that "dollar P&L" is an approximation. **TRIM/REDUCE do not record `returnSinceEntry`** (their trade objects `:75-85`/`:111-121` lack the field); `computeTradeStats` filters `t?.type === 'SELL' && typeof t.returnSinceEntry === 'number'` (`seasonLeaderboard.js:367`), so partial-sell outcomes are excluded from win-rate/profit-factor entirely.

**4. Execution price — closing price, zero friction.** Every trade fills at `ctx.marketData[ticker]?.closePrice`, with `?? pos.currentPrice` fallback for SELL (`:40`), TRIM (`:65`), REDUCE (`:102`), ADD (`:138`); **BUY has no fallback** — `if (!price) continue` (`:170-171`). **No friction/slippage/spread/commission anywhere** — values are bare `shares*price` (`:41`, `:73`, `:109`, `:148`, `:178`); cash moves at raw fill value (`cash += value` `:56`, `cash -= cost` `:165`/`:207`). A grep for `slippage|commission|spread|fee` in the settlement/pipeline files returns nothing.

**5. Rounding & guards.** **Shares:** integer via `Math.floor` (`:68`, `:105`, `:144`, `:174`), each guarded `if (… <= 0) continue`. **Cash:** raw float, never rounded. **Negative-cash guard:** buys cap spend via `Math.min(dollar, cash)` (ADD `:140-143`, BUY `:173`). **Negative-shares / over-sell:** **TRIM/REDUCE `sharesToSell` is NOT clamped to `pos.shares`** — there is no `Math.min(sharesToSell, pos.shares)`. `dollarAmount` uses `computeTotalValue` (`:66`/`:103`), which reads the **stale** prior-settlement `pos.currentPrice` (`:257`, since `recalculatePortfolio` runs only after all trades, `:211`), while the fill uses **today's** `closePrice`. So `sharesToSell ≈ pos.shares × (stalePrice / todayPrice)`, which exceeds `pos.shares` for essentially **any downward intraday move** when the trim target weight is near zero. Result: `pos.shares` goes negative (`:87`/`:123`), `cash` is over-credited for shares never held (`sellValue = sharesToSell × price`, `:88`/`:124`), and then `if (pos.shares <= 0) delete positions[...]` removes it (`:90-91`/`:126-127`). The negative share count never persists, but the phantom cash proceeds do.

**6. Internal consistency & atomicity.** `settleDay` is a **pure function** (deep-clones positions `:29-32`, local `cash` `:33`, no I/O). Cash and positions are always mutated together within each trade iteration, so no cash-without-position desync arises inside the function (the one integrity hazard is the over-sell cash over-credit in §5 — a wrong value, not an orphan). The shadow log (`:443-453`) is fire-and-forget outside the transaction.

**7. ## Q6 — concurrency safety of the season active-entry cap

> Adversarially re-verified: **8/8 load-bearing claims CONFIRMED, 0 refuted.**

**1. `MAX_CONCURRENT_ACTIVE_ENTRIES`.** Module-level `const MAX_CONCURRENT_ACTIVE_ENTRIES = 5` at `api/season/create-entry.js:60` — a hard-coded literal, **not** env/flag/tier-driven (grep finds only `:60` def and `:543`/`:545`/`:547` uses; no `process.env`). It counts **ACTIVE + PENDING** entries across **all** seasons for the user (comment `:533-536`), not just the target season.

**2. Query-then-create vs transactional — transactional, read inside the txn.** Exact sequence inside `db.runTransaction` (opened `:516`): (1) READ season `const freshSeasonSnap = await txn.get(seasonRef)` (`:517`), status re-verified `:524-531`; (2) READ cap query `const activeSnap = await txn.get(activeQuery)` (`:544`), where `activeQuery` filters `userId == uid`, `status in [ACTIVE, PENDING]`, `.limit(MAX_CONCURRENT_ACTIVE_ENTRIES)` (`:539-543`); (3) CHECK `if (activeSnap.size >= MAX_CONCURRENT_ACTIVE_ENTRIES) { err.status = 409; throw err; }` (`:545-551`); (4) WRITE entry `txn.set(entryRef, entryDoc)` (`:553`); (5) WRITE counter `txn.update(seasonRef, { entryCount: FieldValue.increment(1), … })` (`:554-557`). `entryRef` is a pre-allocated auto-ID ref created **before** the txn (`:498`); all slow reads (agent, bundle, rule transform) sit outside it.

**3. Two simultaneous identical requests — can both create over-cap? NO.** Both read the cap query (`:544`), both may pass (`:545`), both attempt `txn.set` (`:553`, distinct random IDs) + `txn.update(seasonRef)` (`:554`). Two mechanisms prevent both committing:
- **(a) Shared season-doc write conflict (repo-visible, strong).** Both read `seasonRef` (`:517`) and write it (`:554`, `entryCount` increment). Firestore optimistic concurrency detects the changed read-set: the second committer retries, and on retry its cap query (`:544`) now sees the first entry, so `:545` catches it. Holds **only** when both requests target the same `seasonRef` — guaranteed for identical same-day solo POSTs, since solo `seasonId` is a deterministic hash of `(uid, startDate, durationDays)` (`buildSoloSeasonId`, `:69-75`; used `:431`).
- **(b) Transactional query read-set / phantom protection.** For requests **not** sharing a season doc (e.g. two solo POSTs with different `durationDays` → different `seasonId` → different `seasonRef`), (a) does not apply; the only shared read is the cap query (`:544`). Firestore native-mode serializable isolation makes query reads participate in the read set, so a concurrent matching insert causes contention → retry → the loser sees the winner's entry. **This is a Firestore server-side runtime property, not implemented or tested in the repo** — the code's only contribution is placing the read inside the txn before the writes.

**4. Uniqueness constraint / marker — none; the count check is the only application guard.** Entry IDs are fresh random auto-IDs (`:498`), so nothing keys an entry to `(userId, seasonId)` and two writes always land on distinct docs. `firestore.rules:743` sets `allow create, delete: if false;` for `seasonEntries` (client creation fully denied; rules enforce **no** uniqueness). The count check (`:544-545`) is the only app-level guard; the incidental serialization is the shared `seasonRef` read+write (a side effect of the `entryCount` increment), which serializes only same-season requests. The guard is a **count ≤ 5 cap, not uniqueness-of-one** — a phantom-protection failure on a cross-season pair would let a user reach 6, not merely duplicate.

**5. Best transactional per-entity uniqueness/claim reference.** `reserveSymbol` in `api/_utils/tournamentAgentLedger.js:364-410`: opens `runTransaction`, reads a **single** ledger marker doc (`const snap = await tx.get(ref)`, `:370`), checks a precondition (`if (heldEntry) return { reserved:false, … }`, `:376`), and writes the claim to the **same** doc only if free (`tx.set(ref, { …, reservations, … })`, `:407`, with `reservations[symbol] = { by: agentId, battleId, at }` at `:406`). Stronger than `create-entry.js`'s guard because read and write target the same single document, guaranteeing a write-write conflict between concurrent claimants regardless of query semantics — the property `create-entry.js` lacks for cross-season requests. Two other same-doc precondition-read patterns: `canonicalOpen.js:112-137` (idempotent write-only-if-absent) and `tournamentClaims.js:117-132` (day-marker idempotency).

## 3. Surprises (things the docstrings / names would not predict)

- **Q1:** `checkSectorCap` is **not exported** despite the module header framing it as the "DR-4 guardrail-binding compilation target"; it is private, reachable only via `applyGuardrails`. It reads **neither** `SECTOR_CAP_MODE` **nor** `DIVERSIFIER_SECTOR_CAP_PCT` — the enforced cap is entirely the passed-in `maxSectorValue`. The whole feature is currently **dormant** (`SECTOR_CAP_MODE='observe'` → no decision is ever overridden, only would-block telemetry logged). On a misshapen/flat/non-tournament portfolio it **fails open** (`totalSlots=0 → null`, never blocks) rather than failing loud. The fixed-6-vs-`held.length` denominator swap (`:629`) applies to **any** tournament `maxSectorWeight` check, not just the Diversifier synthetic cap.
- **Q2:** The identity hash keeps `knobConfigVersion` but strips its adjacent sibling `calibrationBundleVersion` — asymmetric handling of two version stamps. The 406 KB snapshot exists purely as a **CI-lock reference with zero runtime readers**; the header states "ZERO production readers in Phase 2" — the whole registry/hash/snapshot machinery is dark plumbing. Most importantly, the **prompt-template rendering logic — the thing that builds the decision prompt — is explicitly outside the identity hash** and resolves live at tick, so the "identity hash" does not lock the most decision-relevant surface.
- **Q3:** A distributed lease with **no owner and no fencing token** (`:575`) — every release writes only `null` and cannot verify ownership. The **lease timeout (120 s) is smaller than `maxDuration` (300 s)**, so a legitimately-running, non-crashed worker becomes stealable mid-run (180 s window). A stolen lease's original holder then **silently clobbers the new holder's state and nulls its lease** via a plain unfenced `update()`. Separately, `completeBattle` nulls `evaluatingAt` **without ever acquiring or checking the eval lease**. A stale comment at `:2757-2758` still cites a "60s maxDuration."
- **Q4:** TRIM/REDUCE `sharesToSell` is **not clamped to `pos.shares`**, so a downward intraday move (stale weight-basis price vs today's fill price) can **over-sell and over-credit cash** before the position is deleted. **No transaction friction whatsoever** (zero slippage/spread/commission). **Delisted/stale symbols are never liquidated** — a missing price freezes the position forever; `detectStalePrices` only emits a cosmetic warning. TRIM/REDUCE realized gains are **invisible** to leaderboard trade stats (`SELL`-only filter). `computeTradeStats`'s "dollar P&L" uses exit **proceeds**, not cost basis, systematically distorting profit-factor magnitude. And the entire season execution/risk path runs on a cron (`season-daily-evaluate.js`) that is **retained un-scheduled** (BUILD_RULES §6).
- **Q5:** A cold STOCK request makes **two separate `/fundamentals/` calls** (`fetchFundamentals` + `fetchEarnings`) — ~20 fundamentals-credits — yet the 10× cost comment sits only on `fetchHolders`. **`fetchIntradayBatch` is not a batch upstream** — one `/intraday/` call per symbol. **Real-time price is never cached.** **No bid/ask/spread/average-volume** is captured anywhere. **No EODHD credit/quota budget** despite the fundamentals weighting and a commented 3/min limit. Corporate actions are **inferred (raw-vs-adjusted heuristic), never fetched**.
- **Q6:** The cap counts ACTIVE+PENDING across **all** seasons, so a 409 can fire because of an *unrelated* season. The serialization that actually blocks the common duplicate is an **incidental side effect** of the `entryCount` increment, not a purpose-built marker. The header docstring cites `firestore.rules:424` as the create-block, but the real `seasonEntries` `create: false` rule is at **`firestore.rules:743`** (line 424 is an unrelated banner in the battles section).
