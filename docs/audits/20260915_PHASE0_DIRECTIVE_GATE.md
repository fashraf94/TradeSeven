## 2. Q2 — How the gate classifies, and why this was `in_archetype`

**The complete classification set.** `VALID_CLASSIFICATIONS = {in_archetype, flex, core_conflict, user_lever, research_only}` (`api/_utils/directiveGate.js:60` VERIFIED). `DELIBERATE_NULL = {core_conflict, user_lever, research_only}` (`:61`). Anything else, or a missing proposal, is `needsRepair` (`:64-70`, `:76`).

**What decides each.** Nothing in the gate. The label is read verbatim from `parsed._archetypeProposal.classification` (`:65-66`) and only checked for membership in the five-word set. The module header says so: "The model's `_archetypeProposal` is UNTRUSTED. The gate validates it against the archetype's allowlist ... and decides; it never copies model free-text into a directive" (`:9-12`). What it *decides* is: deliberate-null label → null (`:77-79`); otherwise, is `selectedAdjustmentId` on this archetype's menu (`:81-82`) → commit the canonical text with id and version (`:83-97`); otherwise repair (`:99`). The header also states the decision is "a function of (effectiveArchetype, classification, selectedAdjustmentId) only" (`:14-15`).

**Does a hands-off / Zone-4 class exist?** Yes as a label: `user_lever`. The prompt defines it only by example: "the ask is a user lever you don't pull yourself (short / flip / claim)" (`api/_utils/voiceLayerPrompt.js:109` VERIFIED) and "classification core_conflict / user_lever / research_only -> selectedAdjustmentId is null" (`:127`). The original build plan defined the gate exactly this way: "`core_conflict | user_lever | research_only` OR no valid id → `{null,false}`" and "Allowlist-ids-only" (`docs/audits/20260625_ARCHETYPE_INTEGRITY_BUILD_PLAN_V2.md:46-47,:93` VERIFIED). Fit validation was never specified. **The finding is not that Zone 4 has no class; it is that no code, and no prompt rule beyond a three-word parenthetical, decides when the class applies.**

**The classifier's input.** The classification is produced by the same Gemma call that writes the reply: `callGemmaVoice({ systemPrompt, conversationHistory, userMessage: sanitizedMessage })` (`api/agent/chat.js:759-762` VERIFIED), parsed at `:771`, gated at `:839-849`. The model therefore sees the system prompt (identity, game mechanics, output format, the proposal schema, the four zones, the menu, third-path rule, user-levers block, market briefs, battle state, few-shot examples, the elicitation target, phase rules; assembly order `voiceLayerPrompt.js:3077-3130` VERIFIED), the last ten user-initiated exchanges (`chat.js:660-663`), and the user's message. The elicitation target is in the prompt (`:3126` `elicitation`) but is a persuasion instruction for the reply, not a classifier input. The scratchpad is the model's own output. **The decision is model-produced.** `repairUsed` is set to `true` only when the first proposal was missing or carried an invalid id and a second, schema-only call was made (`directiveGate.js:185-197`); `false` in the incident means the first call already returned a valid label and a valid id.

**What `enforce` changes versus `observe`.** In `chat.js`, both modes call the gate identically; the only difference is `normalizedDirective = enforcing ? gate.directive : null` and `effectiveHasDirective = enforcing ? gate.hasDirective : false` (`:852-854` VERIFIED). The gate itself has no mode branch (`directiveGate.js:163-206`; `mode` is accepted and unused, `:166`). **`enforce` validates nothing about fit. It validates only that the persisted text is verbatim from the allowlist, which `observe` also validates and then discards.** `off` runs the legacy free-text `normalizeDirective` (`chat.js:835-836`, `:339-347`).

**Trace for the incident input** ("Swap Core for Support (Full Defense)", Speculator, battle mode, `enforce`, grounding `'shadow'`):

1. `VOICE_GROUNDING_MODE = 'shadow'` (`src/config/featureFlags.js:2137` VERIFIED). `resolveVoiceGroundingMode` returns `'shadow'` for every uid unless the flag is `'canary'` (`:2168-2175` VERIFIED), so `grounded = false` (`chat.js:476`). The **shipped** prompt was sent: shipped `OUTPUT_FORMAT` (`voiceLayerPrompt.js:3084`), shipped `THIRD_PATH_RULE` (`:3119`), shipped `PHASE_RULES` (`:3071`).
2. The shipped phase rules, placed last "highest attention" (`:3070-3071`), open with: "CONFIRMATION → COMMIT THE LEAN (HIGHEST PRIORITY RULE): When the user confirms a direction, accepts your recommendation, or picks from your options ... (3) Set hasDirective to true and write the directive ... Signs the user is confirming: ... they click a suggested action button ... If you're unsure whether they confirmed: they confirmed. Err toward committing the lean" (`:148` discovery, `:185` refinement, `:217` mastery, VERIFIED, identical text). The escape hatch is the last clause: "EXCEPTION — honest pushback: if the direction is genuinely outside how you trade, you may decline in character".
3. The proposal block then says a directive needs an id and that the three null classes carry no id (`:125-127`). To obey rule 2, the model must emit `in_archetype` or `flex` and an id. The third-path rule's "Bias: default to compliance and adjustment; refusal is the rare last resort" (`:108`) points the same way.
4. The gate: `readProposal` accepts `in_archetype` (`directiveGate.js:66`); `evaluate` finds `SP-05` on the degen menu (`:81-82`) and commits `getCanonicalText('degen','SP-05')` with version 1 (`:83-97`); `repairUsed` stays `false` (`:185`); `chat.js` writes it because `enforcing` (`:853-854`).

Model-produced, so the instruction it was given is the one quoted in step 2. No deterministic rule matched; none exists.

## 3. Q3 — How SP-05 got selected over SP-01/02/04/06

**The selection step is the model's.** The prompt instructs "selectedAdjustmentId MUST be one of the ids in YOUR MENU above, or null" (`voiceLayerPrompt.js:125` VERIFIED). The gate does not select, rank, default, or similarity-match; it validates membership (`directiveGate.js:81-82`). The repair prompt lists the ids and asks for "exactly one of [...]" (`:113-118`), which is still the model choosing.

**What the selector sees.** The menu render is `allowlist.map((a) => \`  ${a.id}: ${a.canonical}\`)` (`voiceLayerPrompt.js:2607` VERIFIED): the id and the canonical sentence, nothing more. `policy.riskDirection`, `policy.concentrationDirection`, `forbiddenOpposite` and `ADJUSTMENT_CONFLICT_GROUPS` are not rendered. The non-test readers of the policy and conflict-group data are the lean service and registry (`api/_utils/leanOverrides.js:41`, `api/_utils/leanRevalidation.js:242`, `api/agent/equip-lean.js:189`, `api/_utils/archetypeRegistry.js:32,137`, `src/data/characterLeanPresentation.js:16,73`) and the eval aggregator (`api/scripts/archetype-integrity-eval/aggregate.js:31`) (VERIFIED via grep). **The gate imports none of it** (`directiveGate.js:19`). The model is told in prose that the cautious register is stop/volatility/size (`archetypeAdjustments.js:105`, rendered at `voiceLayerPrompt.js:2611`), but that sentence is not tied to SP-01/02/06 by id, and nothing says SP-04 and SP-05 are two ends of one dial.

**Direction validation.** None. `evaluate` (`directiveGate.js:75-100`) never reads `policy`, never reads the user's text, never reads `originalUserAsk`. **The gate can file an adjustment pointing the opposite way from what the user asked and nothing notices.** `directiveGate.test.js` has no direction or fit row (`:29-170` VERIFIED: rows cover verbatim commit, deliberate-null labels, unknown archetype, and repair paths). Why the model landed on SP-05 rather than SP-04 or the cautious three is not recoverable from the record (ASSUMED: "swap ... for Support" reads as reshaping the book, and SP-04/SP-05 are the only book-shape items on the menu; the model's own `counterOfferText` was not persisted, see Q7).

**What repair would have done.** `attemptRepair` re-sends the same system prompt with a "REPAIR: your previous reply omitted or mis-formed the _archetypeProposal" suffix and asks for a valid id or a null class (`directiveGate.js:104-138` VERIFIED). It triggers only on `no_proposal` or `invalid_id` (`:76`, `:99`, `:188`), is budget-bounded (`:110-112`), and would not have run here: the first proposal was well-formed. Repair fixes JSON shape, not fit.

## 4. Q4 — Where `suggestedActions` come from, and whether they are constrained

**Two chip regimes exist; the incident ran the first.**

*Shipped prompt (what was sent, per Q2 step 1):* `OUTPUT_FORMAT` asks for `"suggestedActions": null OR ["Action Button 1", "Action Button 2", "Action Button 3"]` (`voiceLayerPrompt.js:74` VERIFIED) and "2-3 genuinely different strategic choices as tappable buttons. Each choice should represent a different philosophy" (`:88`). The phase rules add: "ALWAYS present 2-3 genuinely different strategic options ... genuinely different philosophies (e.g., concentrated momentum vs **diversified support** vs sector rotation play)" (`:151` VERIFIED), and the game-mechanics block teaches "Star tier = high risk/high reward. **Support tier = safe floor.**" (`:62`). The elicitation instructions rotate through archetype-blind prompts such as "Present options that range from safe to aggressive" and "Frame a decision around tier placement" (`chat.js:255,:260` VERIFIED). Server-side, the shipped path passes chips through untouched: `suggestedActions = grounded ? normalizeSuggestedActions(...) : (parsed.suggestedActions || null)` (`chat.js:897-903` VERIFIED). **Nothing checks a shipped chip against the allowlist or the zones.**

*Grounded prompt (dark for everyone at `'shadow'`):* chips are `{ kind:'directive', id }` or `{ kind:'ask', text }` (`voiceLayerGrounding.js:1011-1014`, rule `:1028` VERIFIED). `normalizeSuggestedActions` rewrites a directive chip's text to the server-derived archetype's canonical text and drops an off-menu id (`:1066-1074`); an `ask` chip passes through as free text (`:1061-1065`); a bare string becomes an `ask` (`:1055-1059`). So even under the grounded prompt, an `ask` chip can carry any sentence and is sent as a message.

**Tapping versus typing.** In the Battle View chat, `handleActionClick` sends a string chip through `sendMessage(action)` and an `ask` chip through `sendMessage(action.text)`; only a `kind:'directive'` chip goes to `fileDirective(action.id)` and the deterministic route (`src/components/Agent/AgentChat.jsx:1143-1154` VERIFIED; `sendMessage` posts to `/api/agent/chat` at `:999`, `fileDirective` to `/api/agent/file-directive` at `:1070`). The chat route reads `message` from the body and sanitizes it (`chat.js:425`) with no tap marker. **A tapped string chip is byte-identical to typing its text**, which is why the record shows `userMessage: "Swap Core for Support (Full Defense)"` and an `archetypeGate` record: the chip route writes `userMessage: null`, `source: 'chip'` and no gate record (`api/agent/file-directive.js:120-139` VERIFIED). The League arena renders chips only on a grounded answer (`src/components/League/battleArena/useArenaEngine.js:112`), so the incident surface was the Battle View chat (ASSUMED from the chip evidence in the brief).

**Root cause, stated plainly.** Yes. Under the prompt that was sent, the agent may offer any sentence as a tappable option; the prompt actively seeds "diversified support" and "safe floor" framings regardless of archetype; a tap is then a confirmation by the highest-priority rule (Q2 step 2); a confirmation must become a directive; and the only directives that exist are the seven ids. On every such tap the gate is asked to map an out-of-character sentence onto an in-character menu, and any mapping it produces is wrong. The grounded prompt plus `normalizeSuggestedActions` plus `file-directive.js` already close this for `directive` chips by construction (`file-directive.js:1-10`: "`Files:` is true by mechanism: no model is called"), but that path is live for nobody while `VOICE_GROUNDING_MODE` is `'shadow'` (`file-directive.js:172-174` returns 404 unless the caller resolves to `'on'`).

## 5. Q5 — What the voice knows about what was filed

**Ordering.** One model call produces the reply *and* the proposal (`chat.js:759-762`); parse at `:771`; the gate runs at `:839-849`; the reply is used verbatim as `agentMessage: parsed.response` (`:938`) and `agentResponse: parsed.response` on the exchange (`:1023`) (all VERIFIED). The only post-gate edits to the reply are the research-lint withhold (`:917-929`, flag-dark) and the `directiveFallback` line on a failed repair (`:959`). **The reply is generated before the gate resolves and is never rewritten to match it.** Any sentence of the form "that's the lean I'm carrying now" describes the model's own proposal at best, and the model's proposal is not what the record holds when its free-text `directive.text` (shipped schema `voiceLayerPrompt.js:70-73`) is discarded in favour of `getCanonicalText(id)` (`directiveGate.js:85`). The sentence is unsourced by construction. It is also the prompt's own suggested wording: the confirmation rule offers "Got it; that's my lean now." as the model acknowledgement (`voiceLayerPrompt.js:148` VERIFIED), which the incident reply reproduces almost verbatim.

**Does the player see the canonical text?** Yes, in two places. The chat response carries `directive: { text: <canonical>, ... }` (`chat.js:947`) and the persisted exchange carries it (`:1029-1031` via `buildDirectiveRecord`); `deriveChatMessages.js:72` lifts `ex.directive.text` onto the agent message; the directive card renders `{directive.text}` under the eyebrow (`AgentChat.jsx:207` VERIFIED). The This-turn strip renders the battle slot's `directive.text` beside `Filed {t}` (`src/screens/battleView/ThisTurnStrip.jsx:26-27,:71` VERIFIED), live because `BATTLE_VIEW_CONTROLLER_ENABLED = true` (`featureFlags.js:2008`). So in the incident the player saw the agent say "heavy Support floor" and, on the card directly beneath it, "Spread across more names (diversify the chaos)". Three sentences on one screen.

**Does any guard cover this sentence class?** No runtime guard. `renderDirectiveStatus` is code-owned but binary: a null-write turn gets the "No change made to your strategy this turn." line; a committed turn gets `directiveStatusLine: null` because "the committed directive text carries the change" (`directiveGate.js:54-58` VERIFIED). The vocabulary guard is a test over *prompt bytes*, not replies (`voiceLayerGrounding.js:883-926`). `REPLY_LINT_RE` covers anticipation notes only (`:943-947`); the research lint covers research follow-ups only (`:596-616`). The eval's `CLAIM_PATTERNS` heuristic looks for "done / locked in / I've changed" on null-write turns and is informational (`aggregate.js:36-49`). Nothing compares a committed turn's prose to the canonical text it sits above. The grounded confirmation rule would at least tell the model not to describe the lean ("Acknowledge in one sentence. The interface states what was filed. Do not describe what you will do with it." `voiceLayerGrounding.js:656`), but that prompt was not sent.

## 6. Q6 — Zone 4 in code

**Where it exists.** As prose: `zones.outOfScopeUserLever` for degen reads "Doesn't own boring protection, shorts, or hedges as a mechanic. Adjusts its own book by conversation; hands the user toward real levers (tournament: flip a short / claim a volatile inverse; standard: coach a high-ATR inverse/high-beta screen or equip a watchlist) and, for a genuinely scared casual user, names the honest off-ramp (a hedge on their side, or a different agent for the battle)" (`archetypeAdjustments.js:107` VERIFIED), rendered into the prompt as the "OUT-OF-SCOPE / USER LEVERS" line (`voiceLayerPrompt.js:2612`). The off-ramp appears again in `zones.tunableExecution` (`archetypeAdjustments.js:103`). As a rule: `THIRD_PATH_RULE` step 4, "HAND OFF the part you don't own to a real lever the user actually has right now" (`voiceLayerPrompt.js:105`), and the `USER LEVERS RIGHT NOW` block built from the capabilities manifest (`:2625-2640`, wired at `:3119`). As a label: `user_lever` (`directiveGate.js:60`). All of this reaches the one battle-mode Gemma call in `chat.js:759`.

**What does not exist.** No response shape for a hand-off or off-ramp (the schema is reply, directive, chips, proposal: `voiceLayerPrompt.js:64-83,:114-128`); no client affordance; no classification finer than `user_lever`. The charter's "protect the downside" phrasing is not in the zone text (the nearest is "boring protection"), and the eval corpus's only Speculator `user_lever` item is a short/flip ask (`api/scripts/archetype-integrity-eval/corpus.js:98` VERIFIED); no item exercises "protect the lead". Two parts of Zone 4 are contradicted or impossible in code:

- The charter's fear-response is "offer an archetype-fitting volatile hedge" (`ARCHETYPE_DEF_SPECULATOR_2026-06-24.md:35,:56`), and the zone prose tells the model the same (`archetypeAdjustments.js:103`). The user-levers block in the same prompt says "Hedging, options, and sector hedges do NOT exist in this game — never mention them." (`voiceLayerPrompt.js:2635` VERIFIED), and the manifest hardcodes `user_can_hedge:false` (`docs/audits/20260625_ARCHETYPE_INTEGRITY_BUILD_PLAN_V2.md:44`). The model is told to offer a hedge and never to mention one.
- The off-ramp "maybe a different agent for this battle" cannot be taken: `change-archetype.js` throws `battle_active` while the agent has an active battle (`api/agent/change-archetype.js:88,:145` VERIFIED), and the battle's archetype snapshot is frozen at creation (`api/_utils/directiveIdentity.js:11-20` header, `:50-51` resolver). The off-ramp is a sentence the character can say about a door that is locked.
