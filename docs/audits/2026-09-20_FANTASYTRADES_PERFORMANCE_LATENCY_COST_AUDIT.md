## 1. Owner summary

**The strongest navigation findings concern repeated data loading and the amount of JavaScript loaded at startup. There is not enough runtime evidence to identify the dominant cause of the slowdown you experience.** Ordinary section switching does not generally wait for an AI trading decision. News reads already-published stories. Opening a battle reads its saved state. Specific actions, including asking an agent, requesting analysis, and generating a missing opener, can invoke models.

Three changes are worth pursuing first:

1. **Make returning to Forge and other visited sections reuse valid data.** Forge currently starts its rules read, waits for it, and then starts its bundles read. Leaving and returning starts both again. Keep data by signed-in identity, invalidate it after the corresponding edits, and load independent data together. A player returning to their watchlists should see the existing list promptly while freshness is checked. This mechanism was reproduced using the actual mount-effect source and mocked reads; elapsed browser time was not measured.
2. **Reduce the JavaScript required for the first authenticated screen.** The isolated production build emitted a main JavaScript file of **4,467,668 bytes**, or **1,190,932 bytes with local gzip**. Several large sections are eagerly imported. Splitting optional screens is a credible cold-load improvement; the build does not prove how long a real phone takes to download or execute it, and it does not explain every warm return.
3. **Reuse equivalent market facts across battles during background evaluation.** Each battle forces fresh daily history and quotes for its symbols, even when another battle has just requested the same symbols. Share only facts with the same symbol, session, adjustment policy and freshness contract. Keep private portfolios, decisions, scoring and protective-exit authority separate. This has the clearest source-backed potential to reduce external requests and repeated cache writes; the actual bill reduction depends on the market-data contract.

A small measurement package should accompany those changes. It is a prerequisite for claiming success, not a recommendation to build a large analytics platform.

The likely recurring spend drivers are **active battle-days and eligible decisions**, not registered users alone. Repeated quote/history acquisition, decision prompts, learning, research retrieval, and shared news production have different cost shapes. Gemma voice tokens can be inexpensive relative to decision and research workflows, but actual OpenRouter routing and usage are not retained by its shared wrapper. Model downgrades are therefore hypotheses requiring quality comparison, not approved savings.

The most valuable expensive work remains accurate market inputs, deterministic scoring and protective exits, grounded decisions, and durable learning. Remove duplicate acquisition and waiting before weakening those capabilities.

  download/parse entry JS → React + auth readiness → Compete shell
                                        ├─ owned battle subscriptions

                                        └─ root news/market refreshes (independent widgets)

  nav state → mount ForgeWorkshop
                ├─ rules read → bundles read → Forge ready
                └─ overview watchlists API
  enter Watchlists → another listWatchlists load
  leave/remount → local data loading starts again

Open battle
  selected ID (or owner lookup) → battle document listener → portfolio/chat UI
                         ├─ stocks + crypto display quotes [parallel]
                         └─ if missing opener: server read → Gemma → transaction → UI

One scheduled battle evaluation
  scan active battles → expiration/repair → market/calendar gate → fair ordering
  for each battle, sequentially:
    transaction lock/fresh state
      → symbols [parallel: daily history → current quote]
      → quote/scoring/protective authority
      → intraday + technical ranks + market context [parallel where eligible]
      → event/cadence gate → prompt assembly → Haiku
      → validate/guard/commit → durable evidence
      → optional narration(s) [parallel within battle] → next battle

Learning
  completed + pending flag → worker reads bounded queue
    → Sonnet reflection → awaited memory/feedback → milestone?
       → Sonnet consolidation → validation + durable evolution
~~~

The useful layers have different jobs: market acquisition establishes facts; prompt assembly limits and labels context; models propose decisions or explanations; deterministic gates enforce trading authority; transactions protect durable state; client projections control disclosure. Do not collapse them merely because there are many files.

## 3. Navigation evidence

### Timing definitions and measurement availability

For every journey record four independent timestamps relative to the click: **A** visible selected-nav/destination acknowledgment; **U** first real useful destination content; **M** all required data ready and primary action usable; **O** optional widgets/refreshed content complete. A skeleton is A, not U. A disabled composer is not M. Navigation duration is separate from model response duration after sending a message.

No browser interaction timings, request waterfalls, payload captures, render timings, cold/warm distributions or p95s were produced. There was no authenticated synthetic browser fixture available without constructing substantial infrastructure or risking live services. Browser/device/network/CPU conditions and browser cache state are therefore **not measured**, rather than “fast on localhost.” The source and bounded probes still establish actionable mechanisms.

INP measures interaction responsiveness, not destination data readiness. ### Prompt growth, caching and model alternatives

There are useful bounds already: chat takes recent exchanges; evaluation uses a recent-evaluation window; signal source text, watchlist cohorts and Exa excerpts are capped. These do not bound every prompt in tokens. Frozen identity, Forge rules, watchlists, dynamic market rows, research packages and accumulated learning can still grow. Input characters cannot substitute for provider token usage. Record per-block token estimates alongside actual total usage before deleting content.

The highest-confidence prompt candidate is duplicate representation of recent watchlist dialogue, not removing trading constraints. For decisions, preserve the pinned archetype, applicable directives, symbol facts, portfolio revision, evidence timestamps, tool schema and deterministic policy context. For learning, select evidence by documented relevance and retain references to omitted records; do not summarize away losing trades or difficult cases.

Provider prompt caching reuses a processed prefix; application result caching reuses an already-valid answer. They solve different costs. Anthropic requires exact prefix compatibility, minimum 4,096 tokens for Haiku 4.5 and 1,024 for Sonnet 4.6; normal ephemeral expiry is five minutes, with a one-hour option. Tools and system precede messages. Cache creation/read fields must be counted separately; identical request intent alone does not prove a hit. [Official prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Mandates explicitly mark tools/system at [api/_utils/mandateModelCall.js:110](https://github.com/fashraf94/TradeSeven/blob/0871937c9a12e7885ecfb08664f4f612b999d8a5/api/_utils/mandateModelCall.js#L110). A single book's spaced session slots do not create five-minute reuse by themselves. Multiple books sharing the exact vintage/verb-set prefix during one sweep might. First measure eligible prefix length, cache writes, cache reads and same-prefix timing. Concurrent first calls need not all hit a newly created cache.

For a reusable prefix and m sequential calls within expiry, five-minute input cost is 1.25 + 0.1(m−1) times ordinary prefix cost, versus m without caching; it wins at two calls. One-hour cost is 2 + 0.1(m−1), winning at three. With hit fraction h, repeated five-minute writes/hits cost 1.25(1−h)+0.1h; break-even h is about 21.7%. Output and uncached live context remain billable. No zero-cost chat or decision is assumed.

Do not downgrade any model based on price alone. A later authorized comparison should use existing fixtures and owner-approved frozen examples: at least 30 ordinary and 30 difficult cases across archetypes, unavailable/stale facts, multi-directive conflicts, protective exits, HOLD decisions, schema truncation, negative outcomes, milestone learning and sealed information. Require valid structured output and zero new authority/privacy violations; blind review grounding, archetype fidelity and learning faithfulness; report acceptable-success rate and total cost including repair/escalation. This small set cannot establish rare-event safety. Expand only failing/uncertain slices. Existing fixtures are available in the repository; no paid comparison or new test suite was run here.

### Accounting rules

**Period cost = fixed baseline + Σ(workload volumes × full unit cost).**
**Cost per acceptable completed action = all attributable attempt costs ÷ acceptable completed actions.**

For one model attempt, count uncached input, cache creation by TTL, cache reads, output under that provider's reasoning semantics, and paid tools. Do not add cached tokens again as ordinary input, or reasoning again if already included in billed output. Client tool schemas/results consume tokens; local validation is compute, not another model call. Add every actual repair/escalation, failed billable attempt and attributable discarded completion. A timeout alone does not prove a charge, and an abort alone does not prove zero charge.

A feature's full unit cost is model attempts + attributable database + market + compute + storage/egress + telemetry + its explicitly allocated share of shared work. Keep shared news/market costs in one pool and allocate once, or leave them separate. Do not both charge the pool and add the same allocation to every row.

Firestore accounting must include initial query result documents, listener changes and reconnects; distinct overlapping queries; applicable index-entry batches; dependent security-rule reads; writes/deletes, storage/index bytes and egress. Empty queries have a minimum read charge. Queries with at most one range field are exempt from index-entry read charges. A local callback is not proof of a server read; identical SDK listeners can share a target. Reconnection behavior differs with persistence and its 30-minute threshold. Inspect query plans only in a later authorized environment. [Firestore billing semantics](https://firebase.google.com/docs/firestore/pricing).

### Latency attribution without invented percentiles

Use one correlated trace to compute the critical path, including queue age before execution. For parallel tasks use actual overlapping intervals. Never add component p95 values into an end-to-end p95.

- Forge: click scheduling/render + max(optional code fetch, data path) + final render; current rules→bundles dependency is serial.
- Battle entry: optional lazy chunk and battle-identity lookup → document ready → useful render; price refresh and opener are separately timed optional/required states depending on product action.
- Chat: auth/context reads → prompt assembly → model/repair → durable write → response/render. No current data establishes whether network, model or persistence dominates.
- Evaluation: queue/wait behind earlier battles + transaction/data/guards + eligible model + commit/narration. Root cause of missed deadlines requires stage spans and queue age.
- Reflection: queue age + reads + Sonnet + persistence + optional consolidation. A 50-second outer soft budget does not prove two 30-second stages finish in time.

Unexplained runtime time is currently **the entire measured-duration question**: only source dependencies and build bytes are available. Do not replace this gap with estimated milliseconds.

## 7. Architecture decisions

| Decision | Keep present design | Smallest recommended change | Larger alternative / decision |
|---|---|---|---|
| Navigation data ownership | Local hooks are simple but repeat mounts/reads | Identity/revision-keyed session cache and explicit mutation invalidation; parallel independent data | Whole-router/state-library rewrite rejected without evidence. A query library is optional implementation detail, not the objective. |
| Cold JavaScript | One large entry avoids some later fetches | Split verified optional screens; measure first and warm journeys | Aggressive prefetch rejected if it downloads unused code or invokes paid generation. |
| Market acquisition | Per-battle force refresh maximizes independence at high repeated cost | Single-flight fresh facts inside one run; separate history from live freshness | Distributed cache/shared service only if multiple workers remain a measured duplication source and entitlement permits sharing. |
| Job scheduling | Sequential fairness/locks are comprehensible | Reduce repeated I/O, then bounded concurrency if queue age warrants it | Durable queue needs ownership, due time, attempts, lease, idempotency, recovery, fairness and operating budget. Not a default rewrite. |
| Read models | Whole battle is convenient and consistent | Cache immutable subsets and measure bytes first | Summary docs/history subcollections require migration, authorization, consistency and extra writes. Conditional on PLC-008 evidence. |
| Model selection | Existing decision/learning capability retained | Prompt scope, usage capture, result reuse; quality comparison only where a narrower task warrants it | Routing model + cheap attempt + escalation can cost more. No blanket downgrade or consolidation of distinct authority steps. |
| Prompt cache / Batch | Mandate prefix marker and earnings Batch already exist | Measure cache eligibility/hits; Batch only for deadline-tolerant work | Do not put live decisions into delayed Batch merely for 50% token rates. Preserve expiry/revision/session rejection semantics. |
| Hosting | Existing functions/singleton clients | Stage/cold-start and region measurement; limit large imports where attributable | Warm capacity/region move rejected until plan, DB region and latency contribution are known. Region moves have data/operational implications. |

Preserve canonical ATR/scoring constants, prior-close/open guards, protective exits, archetype cadence, frozen battle/vintage context, directives and watchlist revisions, sealed WHY projections, authorization, leases/revision checks, reward/banking idempotency and awaited capture/learning persistence. Repeated validation at a trust boundary is not automatically redundant. A model's verbal explanation cannot replace deterministic execution checks.

Any result cache needs an owner and explicit identity: user/agent, battle/session/mode, market as-of, portfolio revision, directive/watchlist revision, prompt/model/generation version and source-data version where relevant. Public market facts can share independently of private decisions. Invalid or stale results should display a timestamp/pending/error state and disable only actions requiring unavailable fresh facts. A prettier loading state alone is not a backend optimization.
