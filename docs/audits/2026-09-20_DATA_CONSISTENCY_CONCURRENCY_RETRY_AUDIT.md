# FantasyTrades data consistency, concurrency, and retry audit

Audit date: September 20, 2026. Source review with isolated, synthetic local validation.

Reviewed repository: `https://github.com/fashraf94/TradeSeven.git` (local folder name `portfolio-duel`). Reviewed commit: `0871937c9a12e7885ecfb08664f4f612b999d8a5`. Local audit branch: `audit/data-consistency-concurrency-retries`.

## 1. Owner summary

**Verdict: the reviewed checkout does not yet demonstrate reliable competitive results under ordinary retries, overlapping work, and incomplete prices. I would require the first three remediation packages below before treating its agent/League results as dependable under those conditions.** This is a source-based readiness judgment, not a claim that production has suffered these failures. Production configuration, records, and providers were not accessed. Backing and Mandate have materially stronger protections in the tested operations; that does not validate every operation in either feature.

The five most consequential issues are:

| Issue | What a player could experience | Evidence and important qualification |
|---|---|---|
| **An old score can become the final result — DCR-001** | Your agent was ahead at the last evaluation, falls behind before expiry, but the earlier score is used to record a win. | Actual completion code retained an old scoring timestamp, finalized 40 points, and awarded one win. The exact final-price policy needs confirmation; the code does not establish that the cached score is a valid final valuation. |
| **A delayed worker can trade the wrong holding, even after completion — DCR-002** | A protective action already replaced stock A with B. An older decision to replace A wakes up and sells B instead. ### Data and execution boundaries

The browser is React/Vite and initializes Firebase/Firestore directly ([src/firebase/config.js:59-69](https://github.com/fashraf94/TradeSeven/blob/0871937c9a12e7885ecfb08664f4f612b999d8a5/src/firebase/config.js#L59-L69)). The installed and locked relevant versions are Firebase **12.6.0**, its Firestore package **4.9.2**, Firebase Admin **13.7.0**, server `@google-cloud/firestore` **7.11.6**, Vitest **4.0.17**, with local Node **22.20.0**. [package.json:12-16](https://github.com/fashraf94/TradeSeven/blob/0871937c9a12e7885ecfb08664f4f612b999d8a5/package.json#L12-L16) defines separate unit and emulator-rules commands; its dependency ranges are not deployed version evidence.

Firestore transactions atomically commit their writes and can rerun their callback when a document they read changes; reads must precede writes. A write batch provides atomic writes without making an earlier application read a validated transaction read. An increment prevents arithmetic lost updates but does not identify a unique business event. These dependency semantics were checked against [Firebase's transaction documentation](https://firebase.google.com/docs/firestore/manage-data/transactions) and the installed SDK's [transaction retry loop](C:/Users/fashr/portfolio-duel/node_modules/@google-cloud/firestore/build/src/transaction.js:390) and [default attempt count](C:/Users/fashr/portfolio-duel/node_modules/@google-cloud/firestore/build/src/index.js:121). That SDK defaults to five transaction attempts, resets its write batch between attempts, and invokes the callback again with the same transaction object. No live Firestore contention was tested.

Use a stable caller operation identifier, retained request parameters, and an atomic effect/receipt to distinguish a transport retry from a new action. Define delayed-retry retention explicitly. This design basis follows [AWS's idempotent API guidance](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/); it is not itself evidence of a FantasyTrades defect.

The consequential writer inventory was built with repository-wide mutation searches and reverse-caller searches. `mutation-census.txt` retains the mechanical results; `source-evidence.txt` retains the selected numbered source slices. The inventory spans API, browser, and script writers. It is a navigation aid, not proof that every matching line received a full audit.

Agent execution normally transitions admission → active battle → evaluations/swaps → completed battle and stats → pending reflection → memory/consolidation. League transitions forming/draft → battle with user legs and daily banks → final snapshot → ranks/advancement. Portfolio and group transactions are their effect points. Active pointers, query results, prompt context, UI listeners, and quote caches are derived observations; reading them earlier does not grant permission for a later mutation.

## 7. Remediation order

Relative effort is an engineering comparison, not a delivery estimate: S = a small boundary change with focused tests; M = several cooperating writers/consumers; L = settlement/correction across workflows. No implementation or migration is authorized by this report.

### Package A — Reliable final valuation and correction boundaries (first; L)

**Covers:** DCR-001, 004, 005 and options cutoff DCR-017. Components: completion/evaluator, canonical capture/sweep, tournament bank/scorer, advancement finality checks, options resolver. **Dependencies:** owner confirmation of final valuation policy; coordinate terminal fencing with Package B. This delivers the greatest benefit because correct transaction counts cannot make incomplete or wrong-session prices into fair results.

**Prevention/acceptance:** persist required-input manifest, portfolio/leg revision, cutoff/session and completeness; block terminal status and downstream rewards until validated. Preserve deterministic shared scoring and existing daily/event dedupe. Corrected data retries must finish pending work without duplicate stats/ranks. P05–P08 become assertions of the corrected behavior, plus proposed tests 3–4 and the early-options test.

**Regression risk:** confusing cumulative League snapshots with daily deltas, changing long/short closed-leg accounting, flat6/tier multipliers, early-close/crypto semantics, or invalidating valid legacy records. A “zero means missing” patch would incorrectly reject real zero results.

**Detection and recovery:** separately approve read-only queries for old scoring timestamps, mismatched leg sessions, pending closed legs at bank time, premature options completion and recorded-input gaps. Preserve exports before any repair. Revalue from retained point-in-time evidence; then reconcile stats, cumulative results, RP, brackets and any rewards in dependency order. ### Package B — Final-write authority for evaluation and resets (second; M–L)

**Covers:** DCR-002, 007 and ledger DCR-006.
