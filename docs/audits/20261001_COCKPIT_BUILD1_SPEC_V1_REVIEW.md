# Cockpit Build 1 Spec V1 — round 1 review

**Verdict: REVISE.** The proposed answer loop does not yet make its promises enforceable. A filed instruction can reach the model without constraining execution; an answer arriving during a check can produce a re-ask after that check has already traded; and rollback does not specify how existing call directives stop influencing prompts. There are also literal contract and acceptance-test contradictions. A builder cannot execute this document without making additional product and protocol decisions.

| Question | Verdict |
|---|---|
| Are the named HEAD seams present? | Yes for the existing seams, with the map below. The ownership field is `ownerId`, not `ownerUid`. New mechanisms remain proposed. |
| Does B1-2 guarantee hold, ask-first, approved action, or a selected pick? | No. Filing admission, model receipt, and execution enforcement are separate boundaries. |
| Can the re-ask/heard receipts be trusted as specified? | A matched unsuppressed `heard` stamp is the right source for prompt inclusion. It does not prove compliance; re-ask, action reconciliation, and repair need revisions. |
| Does B1-4 inherently violate H2? | No. H2 explicitly permits a separately agreed unobserved-expiry policy. Session-end expiry is compatible if expressed as a transactional policy with an exact calendar cutoff and no fabricated observation. |
| Is per-battle activation sufficient for rollback? | No. Correct the owner field and close the existing-directive, pending-slot, history, and maintenance paths. |
| Can §9 preserve prompt bytes at off? | Yes, with a strictly conditional splice. That is feasible design, not executed proof of an unbuilt change. §9 also substitutes an evaluation block for the contract's chat block. |
| Can this spec be handed to a builder with only its named repository inputs? | No. B1R-1 through B1R-13 below identify the missing or contradictory instructions. |

## 3. Findings and replacement requirements

Severity: **P1** blocks the answer/receipt/activation contract; **P2** is a material correctness or implementation-spec gap. All findings are **CONFIRMED as spec gaps against inspected source**; this is not an implementation defect tally for an unbuilt feature.

### B1R-1 — P1: Filing a directive does not enforce B1-2 at the trade boundary

**Evidence.** Spec §4/L52–62 promises “must not,” “acts on hit,” and a selected next-check trade. The existing gate admits canonical text (`api/_utils/directiveGate.js:139-174`); it does not gate a later executor result. The prompt says “If your next trade is influenced…” (`api/_utils/controlPromptRenderer.js:213-218`). Trade validation checks portfolio, candidates, cooldown, type and conviction, not answered calls (`api/_utils/agentSwapExecution.js:28-89`). Risk execution occurs before prompt assembly (`api/cron/agent-evaluate.js:2012-2016`, `api/cron/agent-evaluate.js:2707-2725`); model execution is at `api/cron/agent-evaluate.js:3573-3579`. The calls phase runs only after the final evaluation commit (`api/cron/agent-evaluate.js:4383-4408`).

**Failure.** A perfectly valid `call_hold_off` can be rendered and heard, while the model returns the vetoed pair and the existing validator accepts it. Conversely, `call_go` or `call_pick` can be heard while the model returns HOLD or ordinary safety gates block the swap. An acknowledgment (`go` against act, `hold_off` against hold, `keep`) creates no directive: an open call is absent from §9's resolved-only block, so the original default is not even guaranteed to be present at the next decision. No endpoint trade is prescribed, but the stronger assertion “every effect goes through the directive gate” is not an execution guarantee.

**Fix as I would write it.** “Separate admission, prompt receipt, and action enforcement. Before build, define the authority of each matrix row and its precedence against platform risk, deterministic exits, proposals, cooldown, exclusivity and portfolio drift. If hold/ask are mandatory, enforce them before every applicable execution path, using the immutable action identity and the answer effective for this check. Audit all six cron executor sites, including proposal processing and deterministic passes, and any other execution writer admitted by the ruling. If approval remains advisory, say ‘request the action, subject to existing gates’ and require an explicit non-execution reason. Never promise a trade based on model compliance. Name all additional fence contacts; §9 cannot be called the only contact until this decision is resolved.”

### B1R-2 — P1: Activation and authentication use a field the battle does not have

**Evidence.** Spec §2/L23 and §4/L44 require `battle.ownerUid`. HEAD writes `ownerId` (`api/_utils/agentBattleService.js:129-132`), verifies `ownerId` (`api/agent/file-directive.js:202-207`), and authorizes call reads by `ownerId` (`firestore.rules:490-498`).

**Failure.** A literal implementation leaves real allowlisted owners off and rejects their answers. Inventing an `ownerUid` alias changes the fenced battle schema or creates competing ownership authorities. The current mismatch is a fail-closed availability defect, not evidence of unauthorized access.

**Fix as I would write it.** “Use the authenticated UID against the fresh server-owned `battle.ownerId` everywhere. Resolve the check mode once from that battle, after the authoritative load, and propagate it to context, admission, tool, prompt, capture and hooks. The endpoint checks parent ownership and resolved mode before reading the call. Missing/invalid owner or allowlist values fail closed; never accept ownership from the body. Add two-owner, missing-owner and removal fixtures using actual battle shapes.”

### B1R-3 — P1: The endpoint and family omit the contract's actual admission gate

**Evidence.** Spec §4/L46 lists ownership/mode/status/state and filing; §5/L66 registers kinds only in `directiveUtils`. Contract §7 requires binding, belief, archetype, membership and budget inside the transaction, a per-archetype canonical family, and one message charged for a divergent answer (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:92-98`). HEAD's membership authority is `src/data/archetypeAdjustments.js:265-305`. The chip implements belief, binding, canonical validation and budget at `api/agent/file-directive.js:181-262`. `directiveUtils` is an activeness helper, not that registry (`api/_utils/directiveUtils.js:38-79`).

**Failure.** A builder can directly file a templated `call_go` after checking only owner and call state, bypassing the deterministic admission contract. Another builder can call the existing allowlist and reject every new call kind. A pending-slot check does not replace expected-thread belief or message accounting. Twenty requests per minute is not the per-battle/League message budget. Picks need stored option, slot and swap-out binding and fresh membership checks; optional counterparts mean some price calls do not yet name a complete executable pair.

**Fix as I would write it.** “Specify a server-only, per-archetype call-action registry and validator, with exact canonical IDs/text versions and a separate ordinary-menu projection so call actions cannot leak into chat/chip menus. Derive action data only from the stored call and validated selected option. Mirror chip owner, agent binding, expected-thread belief, effective archetype, universe/portfolio and budget guards in the same transaction, with all reads before writes. Charge one message per newly accepted directive, none for acknowledgment or retry. State how absent counterparts and stale options are rejected or resolved. The shared writer accepts only an already validated filing plan and must not itself become a gate bypass.”

### B1R-4 — P1: The response wire and second-answer protocol depart from V1.4

**Evidence.** Spec §4/L44–62 calls its new shape “contract §4,” but the literal record differs:

| Item | Contract of record | Build 1 V1 |
|---|---|---|
| `playerResponse` | `{answer, kind:'directive'|'ack', directiveThreadId?, callId, filedAt, heardEvalId?}` | `{answer, at, directiveThreadId, pickSymbol?}` |
| Answer enum | `go, hold, ask, go_now, keep, pick, agree, disagree` | `go, hold_off, ask_first, pick, go_now, keep` |
| Divergent approval | `go_now` against hold | `go` against hold; `go_now` reserved for re-ask |
| Refusal record | `at`, `reason`, `pendingDirectiveThreadId`, optional `pendingCallId` | only `reason`, `at` |
| Second answer | Existing response is not rewritten by state transitions; no `second` wire defined | tests `!playerResponse.second`, but never defines or writes it |
| Acknowledgment receipt | Agent-initiated receipt exchange carrying `callId` | matrix says `playerResponse` only |

Sources: `docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:63-67`, `docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:88-98`. HEAD initializes both `playerResponse` and the top-level `directiveThreadId` at `api/_utils/callRecords/candidate.js:168-171`.

**Failure.** Overwriting `playerResponse` for `go_now` loses the first answer/thread/heard join. Leaving it unchanged leaves the second answer and its idempotency undefined. Returning success only while `open` makes a retry after a hit fail despite the promised identical-answer success. Repeating `pick` with a different `pickSymbol` must be a conflict, not an identical answer. The spec also does not say where its bare `heardEvalId` write lives; V1.4 places it inside `playerResponse`.

**Fix as I would write it.** “Publish an explicit versioned contract amendment for every intentional enum, wire, and second-answer change before building. Otherwise map UI labels ‘Hold off’/‘Ask me first’ to V1.4 values and retain its record. Define immutable first and second answer identities, each thread/filing/heard join, receipt anchor and budget charge. Deduplicate the full normalized answer including selected symbol before rejecting a retry for later lifecycle state; conflicting payloads never overwrite a prior answer. Specify the response's top-level directive reference and return the committed receipt. Acknowledgments write their contract receipt exchange. Include the full pending-thread refusal payload.”

### B1R-5 — P1: `until_ms` lacks enough state to implement its promised lifetime

**Evidence.** Spec §5/L66 carries a deadline but no horizon basis or consumption identity. §5/L72 gives hold/ask a special late-check rule; §7/L82 releases a “consumed” thread on heard; §7/L84 keeps ask-first holding until second answer or horizon. The existing record/slot builders drop every added field (`api/_utils/directiveFiling.js:29-60`; executed probe), while unknown expiry currently stays active (`api/_utils/directiveUtils.js:71-79`). Call deadlines actually live at `horizon.expiresAt` (`api/_utils/callRecords/candidate.js:158`).

**Failure.** A timestamp alone cannot distinguish ordinary expiry from H2's first applicable late check. A `call_pick` or `call_go` with a next-slot hard expiry may be inactive when that check builds its prompt; only hold/ask are given the exception. Releasing a next-check ask merely because it was heard on an earlier pre-slot check removes protection before its judgment. If the release depends solely on a successful later model phase, repeated no-model exits, missing stamps, phase timeouts or rollback can leave a next-check hold active indefinitely. Conversely, a heard slot becoming replaceable lets an unrelated later chat overwrite a still-in-force hold before its horizon. Clearing by field name after an old receipt can erase a newer slot.

**Fix as I would write it.** “Define a complete directive lifecycle: immutable action binding, horizon basis, deadline, answer identity, applicability, pending versus heard versus still-enforceable, and terminal/consumed state. Extend both filing shapes without dropping text/thread/version fields. Freeze one named check instant before every consumer, including control-epoch resolution, and use it for activeness and heard; specify the rule for voice reads without a check instant. A thread can be consumed only by the defined applicable check, with an idempotent consumption identity and repair path, never by arbitrary prompt inclusion. Define go/pick timing and keep/go-now replacement explicitly. Retirement compares the current thread before clearing. State the no-model, failed-model, expired, killed, suppressed, superseded and rollback outcomes, plus the rule for a first answer to an open but already time-expired call.”

### B1R-6 — P1: Re-ask and later-action receipts are not tied to what the check honored

**Evidence.** Spec §7/L84 keys re-ask only on the transaction's current `playerResponse.answer` and hit. The model consumes an earlier in-memory battle (`api/cron/agent-evaluate.js:4072-4079`), and trades before the call transaction (`api/cron/agent-evaluate.js:3573-3579`, `api/cron/agent-evaluate.js:4399-4408`). The flip freshly reads answer state at `api/_utils/callRecords/flip.js:202-225`. The executed pure-helper case returns `{next:'hit', acted:true}` for an open call containing `ask_first`; the helper has no answer enforcement. Once hit, `planFlip` rejects it and the scan excludes it (`api/_utils/callRecords/flip.js:158-167`, `api/_utils/callRecords/flip.js:275-278`).

**Counterexample.** Check E builds its prompt without the new thread. The endpoint commits ask-first while E is running. E executes the matching swap and commits. The flip reads the new answer, hits, and under the proposed rule writes “Go now, or keep holding?” although E never heard that answer and already acted. A separate ordinary re-ask can later accept `go_now`, but the existing open-only pipeline will not attach that later action to the hit call. For picks, the current matching API supports a selected symbol but `planFlip` does not pass it (`api/_utils/callRecords/flip.js:134-165`).

**Fix as I would write it.** “Re-ask/held-off are compliance receipts, not consequences of finding an answer beside a hit. Bind them to the answer effective at the decision boundary, the matching unsuppressed heard/enforcement evidence, and committed action or explicit non-action evidence for that check. Record a late answer honestly instead of attributing it to an earlier prompt. Define an answered-hit reconciliation path for go-now and selected-pick actions; bind whole trade, answer/thread, slot, counterpart and selected symbol. Preserve the original observation receipt. Heard only proves the source stamp's prompt-inclusion semantics; it never substitutes for held, reasked or acted. The ordered transaction that appends the re-ask must make its per-answer event identity create-once.”

### B1R-7 — P1: Off and allowlist removal do not form a complete isolation boundary

**Evidence.** Spec §2/L23 permits sweep terminal writes for removed owners while L27 forbids call reads/writes and freezes records; §12/L113 again requires existing records untouched. Contract off forbids these contributions (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:109-118`; V1.3 expands the collection list at `docs/design/COCKPIT_SPEC_V1_3.md:38`). Existing directive readers consult expiry/integrity, not call mode (`api/_utils/agentEvalPromptAssembly.js:1229-1242`, `api/_utils/voiceLayerPrompt.js:3695-3711`, `api/_utils/controlPromptRenderer.js:121-148`). Spec §6 applies the new pending predicate to all writers, while HEAD's chat overwrites the slot and chip permits belief-checked replacement (`api/agent/chat.js:1071-1083`, `api/agent/file-directive.js:208-214`, `api/agent/file-directive.js:282-286`).

**Failure.** Remove an owner while a call directive remains active: gating publication/tool/endpoint does not remove that directive from the ordinary prompt path. It may continue to influence trades or block later chat/chip filings. If a new pending policy is applied globally at off, a previously valid ordinary replacement becomes a refusal, contradicting behavior preservation. If grounded call exchanges are written, the existing history reader can also admit them at off or let them displace older history unless it filters them before slicing (`api/_utils/voiceLayerGrounding.js:458-498`). Even ungrounded proactive entries count toward the legacy last-ten window before its user-message filter (`api/agent/chat.js:664-667`).

**Fix as I would write it.** “Choose and document a narrow maintenance exception to off, or keep all call stores frozen; these are different contracts and require an explicit amendment if changed. For removed/non-allowlisted battles, suppress call-family directives and call history at every reader before rendering or history budgeting, with no call-store lookup at off. Ordinary directives retain their existing behavior. Scope any changed pending policy explicitly by resolved mode/family. Define whether re-enable may revive prior directives. Test rollback with an actual persisted call slot, its exchange, answer, hit, pending work and ordinary directive—not only call subcollections—and include endpoint, chat, chip, completion and sweep as well as cron capture/tool/prompt outputs.”

### B1R-8 — P2: The sweep drops the very work needed to repair heard receipts

**Evidence.** Spec §7/L82 promises repair for open or hit answered calls, including later retained evaluations. L90 recomputes solely from **remaining open expiry**, deletes when none, and enrolls only open calls. HEAD's publication queue is armed only by new open calls (`api/_utils/callRecords/publish.js:163-185`); the evaluation history is a 150-entry window (`api/cron/agent-evaluate.js:4257`).

**Failure.** Last open call hits, heard write times out, and the queue is deleted. A second answer on that hit creates another thread but no open call to re-enroll. The promised repair may never visit it even while the exact evaluation is still retained. Restricting the direct writer to open/hit can also miss a heard answer whose call expires on that check. A stale repair for the first response must not overwrite the second response's heard reference or clear its newer slot.

**Fix as I would write it.** “Queue coverage includes open-state settlement, every accepted answer awaiting heard/action reconciliation, and thread retirement. Endpoint acceptance and state transitions atomically retain/enroll that work. Delete only when all work classes are complete or explicitly aged out. Repair scans the exact committed thread and answer identity, accepts only unsuppressed stamps, and writes a monotonic first-confirmed reference without replacing newer answers. Define terminal-call eligibility and missing `TICK_STAMPS_ENABLED` behavior. A 150-entry miss says ‘not confirmed heard,’ never ‘not heard.’”

### B1R-9 — P2: The sweep/completion plan needs a shared budget and a bounded recovery protocol

**Evidence.** Spec §7/L86 gives the new worker 20 seconds and promises paging, enrollment and same-transaction completion. The hosting handler already spends a 50-second aggregate budget on reflections, Wire and editorial (`api/cron/process-pending-reflections.js:30-31`, `api/cron/process-pending-reflections.js:65-152`). Existing calls phases protect a shared tail and may skip work (`api/_utils/callRecords/publish.js:56-62`, `api/_utils/callRecords/publish.js:290-309`). Open calls can accumulate across checks; only per-declaration counts are capped (`api/_utils/callRecords/validate.js:289-331`). Completion already writes battle and agent state (`api/cron/agent-evaluate.js:6054-6087`, `api/cron/agent-evaluate.js:6257-6317`).

**Failure.** Giving a late branch a fresh 20 seconds can overrun the handler; putting it last can starve it. Sorting a due queue by an old next-check slot while retaining that same past-due time until session end can monopolize pages. “Enroll any open call” has no query/index/cursor contract. A sweep recomputation/deletion that races minting can lose a newly armed expiry unless both use the same transactional conflict set. Closing every open call in completion is unbounded unless the spec supplies a bound or changes its atomicity promise.

**Fix as I would write it.** “Name the sweep's position and priority within the handler; its deadline is capped by the handler's remaining protected budget, not added to it. Specify deterministic queue order/tie-break, cursor/wrap behavior, index, reconciliation scan and resume state. Distinguish due-to-judge from next-maintenance-at so deferred H2 rows cannot starve others. Re-read parent, call, receipt and queue in the transition transaction; preserve concurrent newly armed work. Define a bounded completion design: either prove a maximum open-call workload that fits its transaction or atomically mark parent/work and finish calls by a documented paged protocol, explicitly amending the all-in-one promise. Do not make a calls repair failure prevent authoritative battle completion.”

### B1R-10 — P2: §9 changes the consumer and content of the contract's calls block

**Evidence.** Spec §9/L101 adds the last five hit/expired records to the **evaluation** directive section, containing default-action prose and answer only. V1.4 requires a **chat** prologue read and `buildCallsBlock` containing open calls, hits awaiting an answer, five resolved calls, responses and heard status (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:100-103`). Existing chat history is not this structured call read (`api/agent/chat.js:664-698`). The proposed field-generated line contains “then I exit/bring it in”; labeling that block “no instruction” does not remove its influence when placed beside active instructions.

**Failure.** A builder can implement §9 exactly and leave chat unable to ground an answer to an open call. Historical default-action text can appear beside active directive text without clearly stating original intent, final answer, heard/action status, or whether it has expired. The five-newest query also lacks an authoritative sort field/tie-break and index requirement.

**Fix as I would write it.** “Retain the contract's bounded chat calls block. If the evaluation history block is additionally intended, name it separately and amend the contract explicitly. Render it as historical declarations and recorded outcomes, with call ID, original intent, answer, heard/action status and horizon/state; do not render an expired declaration as an active instruction. Specify the query, deterministic ordering, projection and whole-row cap/truncation rule. Build the evaluation block in a gated helper and register it in `PROMPT_CONTRIBUTING_MODULES` with the fenced splice, as required by `docs/BUILD_RULES.md:30`. Prove absent reads and exact bytes at off/shadow, and show the complete on text.”

### B1R-13 — P2: Copy and chat event semantics can still misstate the call

**Evidence.** Spec §3/L34 uses top-level conceptual `side`, `level`, `expiresAtMs`, “today's close,” and “then I act.” The stored fields are `condition.side/level` and `horizon.expiresAt` (`api/_utils/callRecords/candidate.js:145-159`). **Failure.** A Friday-after-close declaration can be displayed on Friday as expiring “today” although its deadline is Monday. A later historical line can promise the original default after the player vetoed it. Lint accepts even a sentence that contradicts the typed action because it receives no typed action to compare. **Fix as I would write it.** “Render from the literal stored paths and the stored deadline's ET date/session, including early close and non-today dates. Define one exchange schema and anchor normalization, message type, grounding marker, event identity and retry/recovery rule for declaration, hit, re-ask and each answer receipt. Use a per-eval declaration event and per-call/per-answer transition identities; specify whether re-ask replaces the generic hit line. Suppress an empty calls summary. State how bounded display cadence relates to the uncapped persisted array and how failed appends are repaired without inventing model speech.”

## 5. H2 and B1-4: what survives the attack

**The policy choice itself is permitted.** V1.4 explicitly reserves a separately agreed unobserved-expiry policy (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:118`); Amendment A repeats that obligation (`docs/design/COCKPIT_SPEC_V1_3_AMENDMENT_A.md:16`).
