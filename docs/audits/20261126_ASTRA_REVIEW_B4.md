## Findings

### B4-A01 — A committed creation can acquire a permanent refusal on replay

At the shipped `allowlist` setting, I created a listed player’s book, restored the founder request to its pending state to represent an interruption after the book transaction, removed the player, and replayed the same body. The book still existed. The replay returned **403 `mode_not_admitted`**, marked the request done with that refusal, and returned 403 again on the next replay. R8 says an already-made book is the answer. The wrapper finds that book but re-enters the ordinary creation gate, which checks the list before checking the committed operation. The existing positive recovery row sets the mode to `on`. (`Build:116`, `PF/founderControls.js:270`, `PF/founderControls.js:317`, `PF/ideaBook.js:206`, `PF/ideaBook.js:235`, `PF/b4GroupBooks.test.js:216`.)

**Likelihood and fix.** This needs both an interruption in the book/receipt commit gap and removal before retry. A founder can still operate on the existing book. In the pending-request path, answer success from a committed idea book after verifying its immutable creation identity against the recorded target. Regression row at `allowlist`: pending and already made plus removed → 200, original book ID, replay true. Pending and never made plus removed → 403 and no book. (`PF/founderControls.js:254`, `PF/founderControls.js:319`, `PF/ideaBook.js:237`, `PF/b4GroupBooks.test.js:228`, `PF/b4GroupBooks.test.js:340`.)

### B4-A02 — A malformed token leaves the rest of the player list active

With the synthetic player list `fixture-player,bad/path`, the parser kept both tokens. The allowlist gate admitted `fixture-player` and refused an unrelated UID. A slash is invalid for a book owner under R4. Unset, blank, comma-only and non-string inputs did yield an empty list. The discrepancy concerns the brief’s whole-value fail-closed requirement for malformed input. The parser checks token length after trimming and otherwise performs literal membership. (`PF/playerList.js:37`, `PF/mode.js:64`, `PF/founderControls.js:106`, `PF/playerList.test.js:27`, `Build:112`.)

**Likelihood and fix.** A typo in a deployment list is plausible. In this row only the explicitly named valid player gained access to their own book. Apply R4 validation to the player list as a whole after trimming and dropping empty fields, with a regression row requiring `fixture-player,bad/path` to admit nobody. Preserve the established founder-list parsing contract. (`PF/playerList.js:39`, `PF/playerList.js:45`, `PF/playerList.js:54`, `api/practice-field/book.js:39`, `PF/bookViewRead.js:55`.)

### B4-A03 — Status can label a malformed stored parse entry clean

For a JPM idea admitted after the daily build, I varied just the stored JPM entry. A missing entry produced zero alerts as intended. An object with a rejected row produced `parse_rejected`, and an empty object produced `parse_envelope_malformed`. A present `null` or array produced zero alerts and the text **“clean for the book's symbols”**. The status filter uses a verdict that deliberately groups non-object entries with missing entries. (`scripts/practice-field-founder.mjs:439`, `scripts/practice-field-founder.mjs:451`, `scripts/practice-field-founder.mjs:831`, `PF/dailyCoverage.js:64`, `PF/dailyCoverage.js:115`, `scripts/practice-field-founder.b4.test.js:343`.)

**Likelihood and fix.** The normal report writer constructs an object even for unanswered or malformed vendor data. This row requires a malformed stored value and affects the founder’s diagnostic output. Suppress the late-symbol alert only when the symbol entry is genuinely absent. Regression row: for an otherwise identical after-cutoff idea, missing → zero alerts, stored `null` or `[]` → one alert. (`PF/caParseReport.js:108`, `PF/caParseReport.js:243`, `PF/dailyCoverage.js:118`, `scripts/practice-field-founder.mjs:454`.)
