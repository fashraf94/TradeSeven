## 3. Findings and exact replacement requirements

Severity: **P1** blocks the core evidence/admission/rollback contract or threatens authoritative completion. **P2** is a material specification or handoff gap. All 14 are **VERIFIED specification gaps against inspected HEAD**, not claims that an unbuilt Build 1 implementation already has these defects. Fix paragraphs are **PROPOSED**.

### B1R2-1 — P1: Null model-path action does not prove “the agent held”

**Evidence.** V1.1 L27/L93 set `heldOff` from heard plus null/non-matching `callsCtx.executorResult`. That context starts null (`api/_utils/callRecords/mode.js:56-68`), and its carrier contains only the awaited model-path return (`api/_utils/callRecords/observe.js:175-192`). The risk swap commits earlier at `api/cron/agent-evaluate.js:2012-2029`, refreshes the battle and continues at `api/cron/agent-evaluate.js:2183-2203`; the model-path carrier is populated at `api/cron/agent-evaluate.js:3573-3579`. A guardrail or ordinary veto can also prevent a proposed trade, independently of the answer (`api/cron/agent-evaluate.js:3280-3335`).

**Counterexample.** The persisted call asks to hold an X exit. A risk swap removes X before the prompt; the prompt includes that directive; the model returns HOLD or trades an unrelated slot. The committed heard stamp matches, and the singular model result is null/non-matching. L93 therefore permits “the agent held,” although this same check already exited X. A missing/malformed result must not become positive evidence of non-action either. Even genuinely complete evidence of no execution does not prove the directive caused the restraint.

**Fix as I would write it.** “`heldOff` means this check confirmed no execution on the answered action's affected symbol/slot during a named interval; it does not mean the instruction caused restraint. Use a complete, committed action set for that interval, covering every execution path the claim covers, with explicit completeness. Null/missing evidence is unknown. If Build 1 keeps only the current model-path result, narrow the line to ‘No matching model-path trade recorded at this check’; do not set an unqualified `heldOff`. A risk exit, failed executor, blocked proposal and chosen HOLD are separate outcomes. Match held evidence on the affected leg/slot, not whole-trade equality: exiting X for Z still violates a request to hold X even if the declaration named Y. Test risk-swap-then-model-HOLD, different-counterpart exit, vetoed swap, missing result and genuine no-action.”

This changes evidence collection or wording, not trade authority; it does not ask for enforcement.

### B1R2-2 — P1: Slot identity and cron-only activeness break pending and retirement

**Evidence.** V1.1 L58/L75 read `battle.directive.threadId`; L87 compares `directive.threadId === thisThread`. HEAD uses **`directiveThreadId`** in both builders, the chip's belief check, and the prompt resolver (`api/_utils/directiveFiling.js:29-60`, `api/agent/file-directive.js:209-214`, `api/_utils/controlPromptRenderer.js:123-147`). The proposed `...existing` slot does not add a `threadId` alias. An offline call to the actual slot builder confirmed that key is absent. Separately, L85 makes call activeness depend on two fields that **only cron** attaches; L75 evaluates “still active” on a fresh transaction parent at the answer endpoint, where neither field exists.

**Failure.** Literal belief checks fail for a real current thread, retirement never matches its intended slot, and reusing the specified activeness helper makes every existing call directive inactive in the endpoint. Correcting the field alone does not close that pending-policy bypass. Chat's current write is latest-wins without a client belief check (`api/agent/chat.js:1009-1083`), so “latest-wins, with belief” plus “behavior-preservingly” also needs a concrete definition for chat.

**Fix as I would write it.** “The sole persisted slot/thread key is `directiveThreadId`; no alias is introduced. Define the new request's belief key explicitly (or reuse `expectedDirectiveThreadId`), normalize absent current slot to null, and compare that field. Split `isCallDirectivePendingAt({directive, mode, nowMs, killedIds})` for transactional admission from `isDirectiveActive` for check rendering. The endpoint resolves mode and a finite server instant from its own transaction inputs; it does not depend on cron's private fields. Define killed/suppressed handling explicitly. Retirement reads the current parent and compares family, `directiveThreadId` and immutable answer identity before clearing. A newer slot is never cleared. The shared chat writer records the displaced thread and replacement instant in that same commit; specify whether chat retains HEAD's no-belief latest-wins behavior or adds a versioned belief requirement.”

Also name `__checkInstantMs`'s source and freeze it once. Attach it before `recordControlEpochIfNeeded` (`api/cron/agent-evaluate.js:1691-1702`); require finite numeric instants and deadlines, not coercive `null <= deadline`; do not persist it. Verify every refresh preserves the intended context and that hearing uses the exact prompt resolution, not a later slot. HEAD's refresh merges a fresh document into the same object (`api/cron/agent-evaluate.js:707-718`), so attachment alone is not a definition of which directive snapshot was heard.

### B1R2-3 — P1: The endpoint's literal admission order contradicts its accepted cases

**Evidence.** V1.1 L71/L73 allow terminal pick acknowledgments and identical retries regardless of later call state. L75 then mandates `call open`, current belief, action validation, budgets and pending checks as one admission sequence. It explicitly lists owner but omits the fresh parent's `status === 'active'` for a new directive, required by the contract and chip (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:92`, `api/agent/file-directive.js:202-214`). Parent completion can leave an open call awaiting the proposed closeout sweep. `playerResponse` has no `pickSymbol`; the spec puts selected data into the directive/action identity but does not identify the durable lookup after replacement. HEAD initializes a separate top-level `directiveThreadId` (`api/_utils/callRecords/candidate.js:168-171`) which the new write list never explicitly fills.

**Failure.** A literal `open` guard rejects the terminal `agree`/`disagree` row and the promised retry. A repeat after another chat filing fails belief even though it should return the original result. Applying the pending guard to an acknowledgment can refuse an answer that files nothing. Conversely, a new directive can be accepted against a completed parent with a still-open call if the listed guards are taken as exhaustive. A replaced slot cannot be the authority for deduplicating a later selected-pick retry.

**Fix as I would write it.** “Publish an ordered transaction decision table. Authenticate, verify owner and resolved on before any call read. Read the call and immutable accepted-answer identity. An identical normalized answer returns its original committed response/event without lifecycle, current-slot or budget re-admission; a different answer conflicts. For a new directive require a fresh active parent, legal kind/state/horizon, current belief, canonical binding/membership, pending policy and budget. For a new acknowledgment use its matrix-specific state gate and no directive pending/budget charge. Explicitly state whether terminal acknowledgments remain available after parent completion. Persist the selection in the immutable filing record identified by the response thread/answer ID, name that lookup for retries and reconciliation, and set both contract filing references in the acceptance commit. Refusal records are written only for the refusal cases the amended contract authorizes.”

For `call_go`/`call_hold`, specify fresh action eligibility and absent-counterpart behavior, not only that stored fields are valid. A dead slot or a symbol already moved must not receive text implying a still-available trade. This is admission validation, not a trade guarantee.

### B1R2-4 — P1: Evidence and events can become permanently unrecoverable after a hit or phase failure

**Evidence.** V1.1 L93 adds work to the post-commit calls phase; L115 promises sweep repair of an event missing after transition. The existing phase can skip all work under budget (`api/_utils/callRecords/publish.js:290-309`) and only scans open calls (`api/_utils/callRecords/flip.js:275-278`). `planFlip` immediately rejects terminal calls (`api/_utils/callRecords/flip.js:158-167`); an offline probe confirmed `state:'hit'` plus a matching later trade yields `skip:'not_open'`. L97's queue names only expiry, pending heard and closeout. L93 repairs only heard from retained evaluations, not the transient executor result, held evidence, event backlog or replacement/retirement work.

**Counterexamples.** A hold is heard and its condition hits; the call is terminal, but the hold directive remains active until its deadline. A later check exits despite the instruction; the existing flip scan never revisits that call. Or the trade/evaluation commits but the calls phase times out, losing the only request-local executor result. Or heard is stamped and the last open call settles, the queue is deleted, and its event write fails: deterministic IDs avoid duplicates but do not cause any worker to discover the missing event. Enrolling every accepted acknowledgment into `pendingHeard` creates work that can never resolve because an ack has no thread. Removing a heard hold from the queue can also lose its later retirement.

**Fix as I would write it.** “Separate immutable condition judgment from answer/action reconciliation. Reconcile answered calls independently of `state === 'open'`, through the directive's applicable lifetime, without changing the original observation receipt. Persist sufficient immutable per-check evidence before request-local context disappears; identify it by battle/eval/thread/answer, and explicitly mark missing action coverage unknown. Bind answer-related action/disagreement language to ordering: a trade that predates the answer or a check that never heard it is a recorded coincident action, not compliance or defiance. Queue each work class atomically with its source transition, including action reconciliation, event publication, retirement and supersession. Create event and transition atomically where possible; otherwise persist an outbox intent in that transaction. Acks do not enter heard work. Define terminal, replaced, expired, disabled-stamp and 150-entry-age-out outcomes so each work item either resolves or ends explicitly unknown. Delete queue rows only after every class is settled.”

Keep the first-confirmed heard stamp monotonic. A later complete check should not overwrite its earlier identity; likewise a historical `heldOff:true` must not be rendered as the current/final outcome after a later action. Persist enough event evidence to display both checks with their own times.

### B1R2-5 — P1: The claimed full off freeze does not cover the retained thread exchange or scheduler discovery

**Evidence.** V1.1 L43 promises unchanged prompt bytes and no reads/writes even of queue/state; L89 expressly adds a chip-shaped thread exchange to `chatExchanges`; L115 says history readers are untouched. HEAD's chip exchange has null user text (`api/agent/file-directive.js:120-132`), so its text is normally excluded from model history. But legacy chat slices the last ten **before** dropping null-user entries (`api/agent/chat.js:664-675`), and grounded history also slices before excluding directive filings (`api/_utils/voiceLayerGrounding.js:464-498`). The offline source-slice probe returned 10 ordinary pairs before a cockpit filing and 9 afterward. The existing UI also projects every directive-bearing exchange without a calls-mode gate (`src/components/Agent/deriveChatMessages.js:34-73`).

**Failure.** Removing an owner silences the current directive block but does not restore the old prompt/history: the call's thread exchange still displaces an ordinary conversation turn. “Inactive at every reader” is stronger than “not in the active-directive block.” The existing directive receipt helper can even regard the latest filing as current after a slot was cleared (`src/screens/battleView/deriveReceipts.js:88-105`). Separately, the proposed queue-order/cursor worker must read scheduling records before it knows each parent owner; “skip at off after resolving the parent” does not undo that read. Recording supersession to calls/events during ordinary chat replacement at off would itself violate freeze.

**Fix as I would write it.** “At off/shadow, filter cockpit-family filing exchanges before every history/window budget and before existing directive UI projection, using durable source/family markers already on the exchange, without calls-store lookup. At on, specify their intended history/display treatment separately. Voice's direct current-directive reader remains inactive without a valid check context; its history reader must also apply the exclusion. For scheduling choose one explicit contract: either permit only scheduling-metadata discovery at per-owner off, with call/declaration/event records untouched, or enumerate authorized parents first and never read disabled queue rows. Global off returns before queue/cursor/reconciliation I/O. Ordinary replacement at off writes only ordinary state/history and does not mutate frozen call records; define how any later reconciliation labels that replacement.”

The direct server reader route itself is feasible: eval assembly, control-epoch stamping and heard resolution already pre-gate through `isDirectiveActive` (`api/_utils/agentEvalPromptAssembly.js:1229-1241`, `api/cron/agent-evaluate.js:1701`, `api/cron/agent-evaluate.js:4081-4089`); direct voice uses the same helper (`api/_utils/voiceLayerPrompt.js:3199-3209`, `api/_utils/voiceLayerPrompt.js:3695-3711`). **That limited claim is confirmed; the whole freeze is not.**

The checked-out flag is already `CALL_RECORDS_MODE = 'off'` (`src/config/featureFlags.js:2826`), and stamps are enabled (`src/config/featureFlags.js:2372`). These are source values, not a live deployment read. The existing off golden asserts prompt/write/capture identity and frozen call stores (`api/cron/agent-evaluate.callRecords.offGolden.test.js:437-456`); its unmodified source does not prove the new persisted-directive/history cases.

### B1R2-6 — P2: A one-slot grace is a bounded lifetime, not the H2 reach guarantee

**Evidence.** V1.1 L83 says slot + 15 minutes lets the first check at/after the slot see the directive, calling this “the H2 reach.” H2 explicitly allows a later first reach (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:75`), and the directive contract currently requires a next-check hold/ask to remain active through that first check (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:94`). HEAD's `decideFlip` has no one-slot limit (`api/_utils/callRecords/flip.js:114-121`). The executed helper case at slot + 31 minutes produced `hit`, while L85's proposed deadline predicate was false. Even the following slot's check can start a few seconds after the inclusive slot + 15-minute boundary.

**Fix as I would write it.** “B1-7 defines a bounded advisory lifetime of exactly 900,000 ms after the eligibility slot, with a named check-instant source. It does not guarantee hearing by the first H2 judgment. The call remains eligible for H2 independently of directive expiry; a later judgment may say ‘answer expired before this check’ and cannot imply the answer was heard. Amend contract §7 to this bounded rule explicitly, or supply a different evidence-based lifetime if retaining its first-reaching-check guarantee. Do not describe both as equivalent. Define the no-check, delayed-check and exact-boundary rows, and specify the relationship of answer admission at `horizon.expiresAt` to the longer directive lifetime.”

A pre-slot hearing correctly does not consume a hold under V1.1. Removing the hold-on-heard rule closes that particular round-1 hazard; it does not establish coverage after the grace ends.

### B1R2-7 — P2: The sweep deadline is safer, but progress, paging and reconciliation remain unbuildable

**Evidence.** V1.1 L97/L99 store `{lastDocId}` while ordering by `nextExpiresAt,__name__`, clip work to handler start + 45 seconds, and put calls last. Reflections can start another awaited item up to their 50-second budget; Wire receives all remaining time; Sunday editorial can use the same remaining budget (`api/cron/process-pending-reflections.js:65-79`, `api/cron/process-pending-reflections.js:111-152`). The schedule is a daily UTC window, not a continuous every-15-minute guarantee (`vercel.json:201-202`). The supposed reconciliation index is **collection scoped**, not collection-group scoped (`firestore.indexes.json:580-595`). Build 0 queue rows carry only `{battleId,nextExpiresAt,updatedAt}` (`api/_utils/callRecords/publish.js:163-185`).

**Failure.** Repeated expensive earlier work can leave the calls branch no time at every invocation. The formula protects the handler but does not prove eventual repair. A lone ID is not a complete value cursor for its two-field order unless the worker re-fetches a still-existing snapshot; the row may have been deleted or its ordering value changed. Null-expiry heard-only rows, frozen owners and H2 rows due at their old slot need explicit rotation/wake rules. A global “open calls missing queue” scan cannot be implemented by the existing per-parent index alone. Legacy queue rows lack the two new fields.

**Fix as I would write it.** “Specify the whole query and resume protocol: full ordered cursor values or a defined snapshot-recovery route, deterministic wrap, advancement on skipped/frozen rows, per-battle/per-call page caps, and normalization of legacy queue rows. Separate next maintenance wake from H2 eligibility where needed. Reconciliation either pages parent battles then their collection-scoped calls with two explicit cursors, or uses a separately deployed collection-group query/index; state which. Transactions re-read and merge the queue in the same conflict set as publication/answer enrollment, so a stale pass cannot delete new work. Reserve a bounded share upstream or explicitly declare best-effort progress and its observable starvation condition. Bound every awaited query/transaction and recheck deadlines before writes; timed-out attempts remain unconfirmed and may commit late. Keep all added model-phase receipt work within the existing aggregate calls budget, not a fresh per-call allowance.”

The existing model phase has 4 seconds total, 500 ms status reserve and a protected 12-second tail (`api/_utils/callRecords/publish.js:53-64`, `api/_utils/callRecords/publish.js:312-361`). The worker's 20-second allowance does not enlarge that separate check budget.

### B1R2-8 — P1: Optional closeout writes cannot fail independently inside the completion transaction

**Evidence.** V1.1 L107 says completion closes up to 50 calls in its transaction and, “on any calls-write failure,” sets `closeoutPending` and completes regardless. HEAD commits battle completion and agent accounting together (`api/cron/agent-evaluate.js:6061-6087`, `api/cron/agent-evaluate.js:6257-6317`). A call write error surfaced at transaction commit rejects that same atomic commit; there is no successful partial completion to fall back on inside it. The claimed six-per-check bound is also wrong: the validator caps six **shots**, then appends a fork as another call (`api/_utils/callRecords/validate.js:37-47`, `api/_utils/callRecords/validate.js:325-332`). Repeated declarations can accumulate far beyond 50 open calls regardless.

**Fix as I would write it.** “Fifty is a closeout page size, not a proven maximum. Obtain at most 51 ordered open-call candidates to detect overflow; never enumerate an unbounded set before applying the cap. Define the authoritative failure boundary. Prefer completion independent of optional per-call writes, with a durable bounded closeout handoff and a terminal-parent reconciliation backstop. If preserving an all-in-one fast path, define a second, fresh, idempotent authoritative completion attempt after confirmed failure, excluding optional call writes, and define how unknown commit outcomes are resolved before retry. State how work is recovered if even the queue marker cannot be committed. No timeout is proof the first transaction failed. Preserve hit outcomes, terminal-parent precedence and stats/pointer idempotency.”

This is an implementation protocol amendment, not a request to change score math or fenced completion writers. The existing bare-completion repair discriminator at `api/cron/agent-evaluate.js:6065-6070` must not be accidentally bypassed.

### B1R2-9 — P1: Heard proves prompt inclusion, not that the directive caused a fork

**Evidence.** V1.1 L119 sets `inResponseTo:T` whenever a pick is minted and that evaluation heard T, and prefixes “In response to.” The stamp says the directive was effective in the built prompt (`api/_utils/tickStamps.js:125-151`); it contains no relationship between T and a fork. HEAD's D fork asks for a replacement choice generally (`scripts/declarationsWordingArms.mjs:57-59`). Direct voice already explicitly forbids attributing an unrelated swap to a directive (`api/_utils/voiceLayerPrompt.js:3708-3711`).

**Counterexample.** T asks to hold an energy position; the same check independently proposes a technology fork. Both are valid, but L119 labels the latter as caused by T. One declared event may also summarize several calls, so an event-level relationship can accidentally attribute all of them. “Dormant until round 3 passes” supplies no runtime predicate; the fact that a past replay produced no surviving forks is not an off switch (`docs/audits/20261001_DECLARATIONS_WORDING_ROUND2.md:713-714`).

**Fix as I would write it.** “Ship the response-fork hook, but store only the relationship the evidence proves. Hearing alone permits ‘Directive T was in this check's prompt,’ not ‘In response to T.’ A response attribution requires an explicit per-pick reference in the declared data, validated against that check's unsuppressed thread, and must be labeled agent-attributed rather than proven causal. Keep unrelated calls out of the attributed event. Until that attribution protocol and replay gate are approved, the hook's causal fields/text stay disabled by a named server-side gate with a false pin. Freeze the directive text/version from the check's own filing, never the replacement slot. A successful replay measures propensity; it never turns co-occurrence into per-instance causal evidence.”

This preserves the founder's hook and deferral of the nudge; it corrects what the hook may claim.

Pin the revised serialization and review its exact model-visible delta; report that D's replay results qualify D, not automatically the revised text. Keep the structural off/shadow/on tests and frozen off golden unchanged.”

Do not restore deferred answers to make the old hash true. That would violate the fixed founder ruling.

### B1R2-11 — P2: The renderers still manufacture pick intent and can display unsupported claims

**Evidence.** V1.1 L52's ternary produces `Intent: hold` for every non-`act` default. A stored pick has `defaultAction:null`, not hold (`api/_utils/callRecords/candidate.js:152-159`). L115 derives every event's text from a function that renders the declaration condition/options, not the answer, observation, executor trade or non-execution reason. L54 correctly admits the lint is lexical but still displays every passing `said`. The limitation is explicit at `docs/audits/20261001_DECLARATIONS_WORDING_ROUND2.md:711`.

**Fix as I would write it.** “Dispatch copy by call kind: a pick has a choice/request line and no invented hold default. Authoritative call and receipt lines use typed evidence only. Define event-specific renderers for declaration, answer, heard, action, confirmed non-action, expiry, completion and supersession, with call/answer/eval identity and the evidence instant. A call declaration is not an acted receipt. Preserve actual executor symbol-in/out for action wording, including a declaration with no counterpart. Never derive ‘exited for Y’ from intent. If lexical-passing `said` remains visible, present it explicitly as unverified original agent wording, separate from checked facts; it cannot be an authoritative tile/receipt assertion. A heard timestamp is the check's prompt-inclusion time, not the later repair/write time. An acted time is execution evidence, not the observation receipt's time. `callsCtx.executorResult` currently carries symbols and slot but no execution timestamp (`api/_utils/callRecords/observe.js:186-191`); either retain a verified executor timestamp or say “at the 10:30 check.” Also clarify that `next_check` wording describes a judgment boundary with possible late reach, rather than a guaranteed resolution “by” the scheduled slot.

## 4. What survived the adversarial check

### H2 and the proposed session-close policy

**Compatible in principle.** H2 permits an independently specified unobserved-expiry policy (`docs/CALL_RECORD_FIELD_CONTRACT_V1_4.md:118`). V1.1 L102 now selects the regular session containing the **slot**, uses actual close/early close, distinguishes failed/unknown attempts from committed judgments and rechecks the fresh parent/call. That is the right correction to round 1. HEAD's calendar offers the needed session/slot primitives (`api/_utils/callRecords/horizon.js:48-83`); its check transaction rechecks active parent/open call and creates state plus receipt atomically (`api/_utils/callRecords/flip.js:202-225`). The historical Build 0 conclusion agrees (`docs/audits/20260924_BUILD0_CALL_RECORDS.md:616-633`).

| Scenario | Required outcome under the revised policy |
|---|---|
| Eligible pre-slot observation meets condition | Existing hit behavior remains legal. |
| Slot missed; later check before session close reaches open call | Judge from that later check's own observation, not a reconstructed slot quote. |
| No-model/failed-model/failed transaction | Never invent a heard decision. A committed eligible observation can settle a call under existing H2 rules; a failed attempt cannot. |
| Timed-out check transaction later commits | Sweep re-reads; one committed transition/receipt wins. No “timeout means failure” assumption. |
| Session close reached and no judgment has committed | Sweep may expire a still-open call with null quote and a maintenance source/time, under the agreed policy. |
| Next slot belongs to the next session, including after early close | Use that slot's session close, not the mint day's close. |
| Parent becomes terminal | `ended_with_battle` takes precedence for still-open calls; preserve hit outcomes. |
| Calendar cannot resolve the slot's session | Do not invent a cutoff; leave work explicitly unresolved and report the reason. |

The receipt retains every existing field at `api/_utils/callRecords/receipt.js:35-45`, uses null `evalId`/quote when no check exists, and makes maintenance provenance visible. The spec's phrase “has closed” should be pinned to an exact comparison such as `maintenanceNowMs >= session.closeMs`. These are build acceptance cases; no sweep implementation or calendar integration test was executed here.

### Heard, held and acted are independent facts

The exact unsuppressed-thread join is sound. `deriveHeardStamp` and its prompt-built gate are the correct authorities (`api/_utils/tickStamps.js:138-151`, `api/_utils/tickStamps.js:353-356`). HEAD deliberately stamps a built/sent prompt even when transport subsequently fails (`api/cron/agent-evaluate.js:2688-2693`). Consequently “heard” means **included in that check's prompt**, not successful model comprehension, agreement, or a returned decision. The proposed repair should preserve that definition and expose failure context; it must not derive held from a heard stamp repaired on a failed-model check.

Passing the selected pick to the existing whole-trade matcher is the correct API change (`api/_utils/callRecords/flip.js:134-148`). A late answer cannot be heard by an earlier prompt. Conversely, `filedAt <= promptBuiltAt` alone is insufficient to prove inclusion: the exact heard thread must still match, because the battle snapshot can precede filing. A successful matching trade proves occurrence, not directive causation. Replaced/killed/no-model cases remain distinguishable from “the agent ignored you.”

### Rollback measurement

V1.1 L123 resolves the prior high-level ambiguity by selecting five regular ET sessions **with calls-enabled model calls**, a strict `>3%` invalid-tool-result threshold and no trip on zero data. Implement its denominator as `declarationsPhase` present **and a dispatched call**, not every phase-stamped entry: HEAD writes that stamp on budget/no-model entries too (`api/cron/agent-evaluate.js:4138-4145`). The concrete dispatched-call marker is finite `callMs`, written in the request's `finally` (`api/cron/agent-evaluate.js:2764-2793`); the existing read script already uses it (`scripts/shadow-read-call-records.mjs:268-281`). Define session attribution and report coverage of the retained 150-entry window rather than silently treating a truncated historical window as complete. This is a recipe clarification, not a new threshold ruling.
