Priority 1 — Agent held-set ledger viability
1.1 Wrap coverage — VERIFIED. executeSwapServer has exactly five call sites, all in non-fenced api/cron/agent-evaluate.js: risk loop :890, Haiku autopilot :1300, dormant approved-proposal :1737, dormant expired-copilot :1822, gameplan rotation :1901. All five sites execute inside processAgentBattle, i.e., under the per-battle evaluatingAt lock (:178-195).

Two acquisition/release paths sit outside this coverage:

Initial acquisition at deploy is entirely fenced: stock universe read (decide.js:122-127), shortlist validation (:220-244), portfolio validation (:692-733), createAgentBattle (decide.js:615 → agentBattleService.js:42-202). Non-fenced wrapping is only possible around the HTTP call: the deploy response returns the battle id and full portfolio (decide.js:661-673), so an orchestrator can register the held set after deploy returns — with a window between battle creation and registration. Reporting this exactly; not proposing a resolution.
Release at expiry happens in non-fenced completeBattle (agent-evaluate.js:2132-2258) and in fenced decide.js:468-472 (expired battle marked completed before re-deploy). A held-set that is derived (rebuilt from status=='active' battles) rather than incrementally hooked avoids needing anything inside the fence; an incrementally-maintained one would need a hook at the fenced site. Both facts VERIFIED.
1.2 Transaction shape — VERIFIED, and this is the load-bearing constraint. executeSwapServer opens its own db.runTransaction internally (agentSwapExecution.js:140) and its signature (:105) accepts no transaction handle. Its transaction reads the battle doc (:141) and writes: portfolio.{tier} array, portfolio.bench.stocks, portfolio.bench.crypto, thresholdHistory, trades, scoreState.tradeCount, updatedAt (:306-316). Consequence: a Firestore transaction opened at the call site cannot include those battle writes — true atomicity of (held-set doc + battle doc) requires fence contact. The non-fenced alternative shape is two-phase: a reserve transaction on the held-set doc (read held-set, write claim) before the swap call, then a release/compensation on swap failure (the call sites already have catch blocks at :926-928, :1314-1319). The existing eval lock (:178-195) assists by serializing all swap paths per battle, but it is per-battle only — it provides zero cross-agent serialization on a shared held-set doc, and it does not constrain the design (it's a cronState.evaluatingAt field, not a doc lock). Pre-transaction network I/O is deliberately kept outside the internal transaction (agentSwapExecution.js:108-138), so wrapping the call in a held-set lease adds no transaction-side I/O hazard.

4.3 Fan-out budget. Each deploy is its own HTTP invocation with its own 60s maxDuration — the binding constraint is the orchestrator's budget and the deploy rate limit (3/min/IP would cap a naive single-source orchestrator at ~3 deploys/min → 16 agents ≈ 6 minutes minimum even ignoring latency). In-repo patterns available: the eval cron's time-budget deferral (process until 50s, defer the remainder to the next tick — agent-evaluate.js:126-132); bounded-concurrency batching with sleep (decide.js:526-563, PRICE_CONCURRENCY=5/200 ms); and multi-tick cron cadence (snake-draft-autopick every 10 min). 4.4 Failure semantics today — VERIFIED. A mid-pipeline throw lands in the catch (decide.js:674-687): deployingAt cleared, 500 returned, no server-side retry (only the Anthropic SDK's internal maxRetries: 2, :40).
